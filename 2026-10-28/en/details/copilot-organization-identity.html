An identity for the running service

A background service should have an accountable owner even when no employee is sitting at a keyboard. GitHub’s new preview lets an organization-installed app supply that identity for Copilot requests. This addresses the operational coupling between a person’s login and an automated workload: a staff change should not leave a service’s billing identity unexplained. It does not decide what the service should do with a repository or which tools deserve access. Those remain separate permission questions. The distinction also separates this update from assisted permissions, covered previously: one concerns the identity making requests, while the other concerns approval during execution. Teams can adopt one without treating them as the same release.

A short token has an operational lifecycle

The service obtains an installation token and passes it through the SDK’s explicit token option. Turning off discovery of a logged-in user also changes how credentials are found, so an environment variable should not be assumed to rescue a missing explicit option. Tokens expire after an hour. The documented refresh procedure involves a new token and restarting the relevant client or runtime. For a long job, that creates a practical integration question: what progress survives a restart, and which external effects have already happened? GitHub Actions has a separate built-in-token route with its own policy. Copying that configuration into an external service would blur two different authentication paths.

Read-only does not mean cost-free

The permission’s Read-only label deserves careful interpretation: it authorizes requests that consume organization credits. Existing model restrictions and spending controls still apply, but the documentation does not offer an independent budget for each installation. An alert-only budget also leaves requests running. This matters when several services share the same organizational allowance. A team may know exactly which application generated usage without being able to reserve a separate quota for it. Approval therefore needs an operational owner and an expected workload, rather than only a permission-name review. The cost of a completed job still depends on actual requests and model choices; the identity change does not establish a fixed task price.

Attribution and stopping use different controls

App attribution currently lives in exported usage reports. The app identifier can be matched to the organization’s installation listing; the ordinary usage view does not provide the same breakdown. Stopping an installation is more direct, through suspension or removal, but that also removes its access to other organizational resources. A single app carrying many unrelated responsibilities therefore has a wider interruption boundary. Keeping ownership and service responsibilities legible makes this control easier to use during an incident. These are deployment consequences of the documented interface, not measured reliability improvements. The public preview does not supply evidence that every long-running workload will survive credential rotation without additional application work.
