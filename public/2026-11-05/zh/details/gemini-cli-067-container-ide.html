隔离代理后仍能逐项看改动

Gemini CLI Companion 把打开的文件、光标和选中文本提供给命令行代理，并把建议修改放进编辑器原生差异视图。此前代理位于 Docker、Podman 或 gVisor 容器，编辑器位于宿主时，这条连接不能正常工作。0.67.0 稳定版收录了桥接修复，开发者可以继续在隔离环境里执行代理任务，再回到熟悉的编辑器接受、拒绝或直接调整改动。这减少了在终端读大段补丁、手工找原文件的步骤；它没有替人判断代码逻辑，也不意味着所有沙箱都已获得同样支持。

令牌留在宿主，桥接只处理有限动作

原问题不是简单缺一个端口：Companion 只监听宿主回环地址，且要求当前窗口的认证令牌。新实现由宿主启动器连接扩展，再用 docker exec 或 podman exec 的标准输入输出管道，接到容器内部的 Unix socket；容器不需要拿到宿主令牌。桥接仅允许 openDiff、closeDiff 和上下文通知，并将文件路径限制在 IDE 工作区内。这个设计让“容器能请求显示差异”和“容器能任意操作宿主”成为不同能力。实际文件挂载与其他工具的权限仍需分别配置，不能只凭这个桥接就概括整套环境的安全性。

启动顺序和审阅选项会影响体验

版本固定的文档要求在启动 CLI 前让扩展处于运行状态，容器镜像里要有 Node；默认镜像满足后者。开发者可以查看 ide status 确认连接到哪个编辑器，以及代理收到哪些最近文件。Companion 的文件上下文只覆盖十个最近访问文件，选中文本也有长度限制，并非整个项目自动完整可见。差异视图允许先改再接受，但若选择会话内全部允许，后续改动会自动接受，不再逐次显示。测试流程需要确认审阅方式真的符合团队习惯，尤其不要把连接成功和每次改动都经人工确认混为一谈。

稳定版日期与作者测试范围分开看

相关合并请求在十月已进入代码库，本期的新节点是十一月四日稳定版发布，不应把早期合并或预览版日期抹去。作者报告在 Linux 上以 Docker 和 runsc 验证连接、越界路径拒绝和退出清理；其 Podman 实机测试受已有映射问题阻碍，只覆盖启动器单元测试，Windows 与 LXC 也不能被写成已经同等验证。团队可先用一个无关紧要的文件测试接受、拒绝、扩展重载和取消，检查实际文件与残留进程。这里没有运行这些测试，也没有给出性能提升数字；版本文档比仍保留旧网络说明的网页缓存更适合复核本次机制。
