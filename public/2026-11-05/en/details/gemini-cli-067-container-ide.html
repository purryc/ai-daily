Review changes while the agent stays isolated

Gemini CLI Companion supplies open-file, cursor and selected-text context to the command-line agent, then presents proposed changes in the editor’s native diff view. That connection previously failed when the agent ran in a Docker, Podman or gVisor container while the editor remained on the host. Stable release 0.67.0 includes a bridge so developers can keep execution isolated and still accept, reject or adjust changes in the familiar editor. This can remove the detour of reading a large terminal patch and manually locating its source file. It does not judge the code’s logic for the user or establish equivalent support for every sandbox.

The host retains the token and brokers limited operations

The original problem was more than a missing port: Companion listens on the host loopback address and requires a token for the editor window. The new host launcher connects to the extension, then uses docker exec or podman exec standard input and output with a Unix socket inside the container. The host token stays outside. The bridge permits openDiff, closeDiff and context notifications, confining file paths to the IDE workspace. Asking the host to display a diff is therefore separated from arbitrary host access. File mounts and other tools still require their own configuration; this bridge alone cannot characterize the security of the complete environment.

Startup order and review choices matter

The version-pinned documentation requires the extension to be running before CLI startup and Node to exist in the container image; the default image supplies it. Developers can inspect ide status to identify the editor connection and recently opened files received by the agent. Companion context covers ten recently accessed files and limits selected text, rather than exposing a complete project automatically. The diff view permits editing before acceptance, but choosing allowance for the entire session makes later changes auto-accepted instead of individually displayed. A trial should therefore check the actual review mode. A connected editor does not establish that a person inspected every modification.

Separate the stable release from the author’s test scope

The underlying pull request entered the repository in October; the new event here is the November 4 stable release. Earlier merges or previews should not be erased from that chronology. The author reports Linux checks with Docker and runsc for connection, rejected out-of-workspace paths and cleanup. A pre-existing mapping problem prevented a live Podman check, leaving launcher unit coverage; Windows and LXC cannot be described as equally validated. Teams can use a disposable file to exercise acceptance, rejection, extension reload and cancellation, inspecting files and leftover processes. These tests were not run for this issue, and no performance gain is claimed. Version-pinned documentation resolves stale website text about the older network approach.
