Claude Code 2.1.317 · Developer-tool update · official release

Claude Code can stop an action when its SDK check fails

The checker can fail too

A developer connecting an agent to file writes, network requests or business tools often inserts a callback to decide whether an operation may proceed. The callback can fail independently of the proposed action. Version 2.1.317 adds an SDK option that blocks the action when that callback fails. This is a failure-handling contract, not a policy generator. It cannot make an incorrect rule correct. A callback that consistently returns permission may be perfectly reliable software while providing no useful review. Teams still need to define which operation is being checked and what evidence the decision requires. The release gives that check a clearer failure behavior.

The version scope matters

The hook reference dates the analogous command and HTTP option to version 2.1.295. This update should therefore be described as SDK callback support, not the first fail-closed mechanism anywhere in Claude Code. The documentation also distinguishes events before and after tool execution. A preflight check can prevent a call; inspecting a result afterward cannot undo an already completed write. An integration should place the decision at the appropriate point before designing notifications around it. A background audit can be useful for investigation, but it cannot offer the same preventive behavior as a synchronous decision made before the operation begins.

Permission problems need visible explanations

Other changes make permission-relevant state more visible: schedules warn about connectors the user did not request, sending the account email prompts a check, and Desktop reports when organizational settings have not loaded. These concern different boundaries rather than one overall security rating. For an interface designer, the useful question is whether a person can tell what the pending task has connected to and what approval would authorize. Two simultaneous requests need distinguishable targets. A visible button without a clear object can still produce an uninformed decision, even when the underlying permission mechanism is functioning as designed.

Validate the integration with failure cases

A practical integration test uses an isolated destination and exercises permission, refusal and checker-error outcomes separately. Inspect the actual write, the message shown to the user and the retry state. After fixing the checker, reconsider whether the original operation is still appropriate instead of blindly resuming a stale request. Duplicate approval clicks should not create duplicate writes. This is a proposed test, not one performed here; no escape rate or time saving was measured. The release does not replace existing account or model-access requirements and supplies no separate price. Existing integrations should first identify whether they use SDK callbacks or another hook mechanism.
