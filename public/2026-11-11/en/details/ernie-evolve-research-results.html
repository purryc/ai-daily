Specify the optimization problem before selecting a route

Baidu’s November 9 disclosure describes a system that receives code, objectives and evaluation criteria, then iterates on implementations. It is a research workflow, not a consumer optimization button or an announced purchasable agent service. The product problem is continuity between experiments: a promising final version is less useful if nobody can explain why earlier branches were abandoned. Connecting code versions to findings could help a team distinguish a justified change of direction from repeating an unsuccessful idea. That is an interpretation of the design, not a measured reduction in research time. No instance of the automated system was operated for this report, and no service pricing is established.

Keep the experiment author separate from the answer key

The described workflow separates planning and editing from evaluation and review. Its evaluator sits outside the editable repository, and candidates that exploit the test or exceed scope are rejected. A practical implication for developer tools is that boundaries need to be inspectable artifacts rather than instructions buried in a prompt. The tested revision, evaluation entry and acceptance conditions should remain identifiable. Users also need to distinguish a code failure from an environment failure or a mistaken objective. An architecture diagram cannot prove that every form of test exploitation has been excluded. Adopting this pattern would still require the team to define correctness and interruption conditions for its own task.

Inspecting results is different from receiving the system

The result repository contains final implementations and measurement logs, with executed code or its hash recorded for checking. Those artifacts do not amount to the full research orchestration system. The root README also distinguishes hardware and data requirements between experiments. A team considering the work could first ask whether one published implementation addresses a bottleneck it actually has, before budgeting for reproduction. Public code does not make accelerator access free or eliminate environment preparation. This review read the repository root; deeper directory retrieval was blocked, and no script was run. The distinction matters because an inspectable final result supports a narrower claim than independently reproducing the search that discovered it.

[S83]

Avoid turning selected artifacts into a universal performance claim

The technical report discusses both public tasks and internal inference optimization, but workload-specific gains should not become promises for arbitrary requests. There is also an important completeness boundary: the blog discusses a 235-problem kernel evaluation, while the repository root lists seven released kernel artifacts. That is not evidence that the complete aggregate evaluation can be reproduced from the published folder alone. A useful adoption review separates algorithm changes, hardware adaptation and environment setup, then states which accuracy, latency or determinism requirements must survive. Fewer experiments, lower total research cost and sustained production benefits each need additional measurements. None was independently established here, so vendor results remain evidence to inspect rather than a universal purchasing claim.
