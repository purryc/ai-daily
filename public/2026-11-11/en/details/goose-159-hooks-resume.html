Approval precedes checks with side effects

goose 1.59 exposes reusable GDK operations for approval, pre-call checks, post-call observation and completion decisions. A developer routes model requests through a state machine whose approval policy can allow, deny or ask the user. Only approved requests reach a pre-call hook. The implementation explanation emphasizes persisting approval before a slow hook runs, so a crash does not repeat the entire approval stage. This is an integration interface, not automatic authorization for every tool. It gives applications a place to implement their own policy, while leaving the host responsible for operation ordering, persistence and actually presenting confirmation requests to a person.

A final answer can be accepted or sent back

A stop hook runs when the model supplies a final answer without tool calls. It can accept completion or return a reason to continue, such as a task claiming success while its tests remain unsuccessful. The pinned README limits this return-to-work loop to eight denials per user message by default and describes errors as terminating the run unless the host handles them differently. That default is loop control, not a quality score or a universal recommended threshold. A post-call hook observes each result but cannot rewrite it. These separate points distinguish permission, execution outcome and completion criteria, without proving that a particular policy implements those judgments correctly.

A completed delegate can receive a follow-up

Completed delegates can now receive follow-up instructions while retaining their earlier context. Previously, trying to resume one was rejected as already completed. The caller supplies the delegate identifier and new instructions; the system waits for a new answer rather than treating the earlier answer as completion of the new request. A user could ask a subtask to review a module and later explain an omission without restating all the background. New instructions are required because there must be new work to perform. Retained conversation history should not be confused with a guarantee that files, permissions and external tool state remain unchanged. The follow-up still needs a defined scope.

[S72]

Stopping and recovery have explicit limits

Cancellation drops a running asynchronous step and marks unanswered tool requests as interrupted, according to the GDK documentation. It cannot roll back an external action or blocking work already started. Hosts that drive the state machine themselves must also finalize interrupted work and preserve output already received. This matters for tools that send messages or write files: before resuming, the application should check whether the action occurred instead of interpreting cancellation as proof of non-execution. The original release API dates this version to November 10 at 17:17:02 UTC. No SDK runtime test was performed, and an open-source repository does not imply zero model-service or deployment cost.
