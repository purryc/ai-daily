OpenHands ties automations to agent profiles and displays spending beside its cap

A preset can select more than a model

OpenHands 1.38 lets prompt and plugin presets select an agent profile, so a recurring task can use a defined model and tool combination. Selecting a profile locks the model control to that profile; ACP agents are labeled ACP rather than incorrectly showing another LLM profile. The control depends on a service capability. A backend without presetAgentProfiles support still presents only the model picker, so upgrading Canvas alone does not guarantee availability in every deployment. For a task intended to read files or use a terminal, the selection makes its execution configuration more visible. The tools and identity actually supplied by the service still need checking.

Edit executable configuration alongside its trigger

A plugin automation’s trigger filter and executable configuration may refer to the same repository set while requiring separate maintenance. The new editor loads saved configuration as JSON and exposes it to the help agent, which can propose both changes together. Proposals do not persist until the user saves. Plugin source, pinned references and runtime selection are preserved rather than freely replaced by the proposal. Non-object JSON is rejected locally and backend schema errors remain visible. This reduces context switching and missed configuration edits. It does not determine whether adding a repository should also broaden the events an automation is allowed to handle; that relationship still needs review.

Budget display keeps values above one hundred percent

The Usage panel now pairs accumulated conversation spending with its existing configured cap. Maintainer documentation says values and percentages above the cap remain visible; only the bar width stops at full scale. If the server supplies no cap, the meter stays hidden. This adds neither a new accounting counter nor enforcement logic, so the display is not a promise that spending cannot exceed the limit. It also distinguishes planner metrics from the parent conversation to avoid pairing one task’s cost with another task’s cap. Readers should check ownership and refresh timing rather than infer that a warning color means execution has already stopped.

Interrupting an agent is different from pausing its sandbox

Release notes also correct the composer’s stop button to interrupt the agent instead of pausing the Cloud sandbox, and retain Docker conversation workspaces in a persisted volume. These changes concern user control and file persistence separately; they do not establish lossless recovery for every task. The release timestamp is November 10 at 04:59:49 UTC, earlier than this issue’s main window, so this is a recent supplement following the previously covered 1.37 automation diagrams. An adoption check could inspect one saved configuration, an interrupted task and files after reopening. Those tests were not run here, and costs shown in maintainer fixtures are not general product pricing.
