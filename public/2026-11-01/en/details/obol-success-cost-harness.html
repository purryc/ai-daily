Putting the bill beside the task result

The maker introduced Obol in an October 30 community post as a small research tool for a practical accounting problem. Repeated history, tool calls and retries consume tokens, yet a cheap individual call does not imply a cheap completed task. Obol gives the same tasks to different strategies and records correctness, estimated cost per task and cost per success together. These are not open-ended chat ratings: order and lending questions have numeric answers computed directly from the data in Python. Results can be broken down by strategy and task to reveal where spending still produced an incorrect answer. The release supplies readable implementation and experiments, not a commercial agent platform or a claim to represent all production work.

How a one-shot program hides a failure

The harness compares a stepwise agent that observes a tool result before choosing its next action with a model that writes one Python program to run the tools. A prewritten program can avoid repeated context transmission, but may miss unusual tool responses. The experiment log records silent mistakes such as looking up the wrong customer name and receiving an empty result, comparing against a misspelled product value, or summing quantities when the question asks for an order count. The program still returns a valid number, so escalation triggered only by crashes never asks a stronger model to retry. Execution traces and final answers therefore need separate inspection. Successful execution alone is not successful completion of the requested task.

The checks themselves have transfer limits

The author adds trace checks for suspicious empty lookups and comparisons against values absent from tool results, then can pass a rejection reason to the next model. The experiments do not present this as a solved mechanism. Checks designed in the order world failed to transfer to the lending world, where mistakes included ignored pagination and taking the length of a dictionary. Escalation can also replace a cheap wrong attempt with an expensive wrong attempt. The record retains predeclared criteria and held-out tasks: none of three holdouts met the author’s complete win threshold. These failure details help a reader identify the kind of mistake in their own workflow instead of relying on a single savings multiple.

Local experiment costs are not provider bills

The reported runs use two small Qwen models through Ollama. Token counts come from execution, while dollar costs are calculated using a hypothetical price table. The repository explicitly says other provider backends have not all completed live end-to-end testing, so the list of interface names is not a verified compatibility list. The MIT-licensed code and documentation allow readers to substitute models, register read-only tools and add tasks with Python-computed answers. It executes model-written Python. Although syntax restrictions, blocked imports and a timeout exist, the author explicitly states that this is not a sandbox. Real write operations, ambiguous goals and larger tool outputs exceed the current toy worlds and limit how directly its results inform an actual cost decision.
