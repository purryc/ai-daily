An action response still needs a controller

RoboAPI receives an image and robot state describing the same observation, together with a written task, and returns predicted actions. Developers can use a hardware-connected local runtime or call the model and adapt its output to an existing controller. The first-call example only prints actions. That separation lets an integrator check imagery, coordinates and output structure before commanding movement. Continuous operation needs a new observation after action; the initial picture is not a lasting description of the workspace. A successful response proves inference completed, not that an object was grasped. Sessions and execution receipts record actual progress, and unexecuted actions must be discarded after a stop or connection failure so a retry does not repeat stale motion.

The wrist viewpoint is part of the interface

The reference hardware places a fisheye action camera near the gripper, giving the model an end-effector-oriented view of manipulation. The guide specifies UR-family arms, a Robotiq 2F-85, a Linux host and particular camera and lens combinations. This is more specific than plugging in any available webcam. Projection, mounting position, gripper geometry and coordinates determine whether observations match the expected interface. The assembly also constrains the adaptive folding of the gripper fingers. The image and the physical control point must agree before predicted actions can be interpreted correctly. A different arm additionally needs suitable drivers, feedback and stopping behavior; similar pictures alone cannot establish compatible kinematics or a dependable control connection.

Connect visual prediction to action learning

Poke-Aurora learns future visual observations alongside robot actions. The company describes a coupling mechanism intended to let those learning processes inform each other while preserving their original computation paths; fuller technical detail is still promised. A mechanism name is not a reproduced generalization result. The announcement reports success on an internally constructed evaluation, but another bench changes lighting, objects and assembly. Those results cannot be transferred directly to a new installation. Selected demonstrations span arranging objects and interacting with the surroundings, giving external teams concrete task families to examine. The practical change is access to a shared model for those experiments, rather than having to collect and train a separate task-specific model before every small evaluation.

Repeated attempts need an explicit stop

This is a noncommercial technical preview, not a general production service for every business. A user still needs suitable equipment, installation, calibration and movement checks. PokeBot notes that a held object can obstruct the single camera, English instructions generally work better, and long tasks can benefit from shorter steps. The system may continue attempting a task after failure. Persistence can help with a missed grasp, but it makes a clear stop mechanism essential. The installation guide explicitly says closing the browser does not stop a running task; Robot Stop does. Software motion limits constrain commanded targets rather than enclosing the whole arm or avoiding obstacles. Model access lowers an experimentation barrier while leaving physical operation and intervention with the integrator.
