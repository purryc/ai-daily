An invented method gets a useful hint

A person asking AI for a small task-management panel may not know whether a failure belongs to the application or the generated extension. An earlier issue captured exactly that situation: the reporter said the plugin was AI-written and encountered a missing showIframe function. The October 31 merge addresses this handoff. Reading an unknown PluginAPI member produces suggestions for real names and a link to the complete type definitions. The runtime does not silently substitute another operation. The author still needs to understand and edit the call. The error message becomes concrete input for the next repair attempt instead of requiring another vague description of a broken application.

Host code and embedded pages have different capabilities

A plugin can contain host-side JavaScript, or present an interface in an embedded HTML page. Both surfaces expose a PluginAPI name, but they do not provide identical capabilities. The new diagnostic can explain that a real method belongs only in the host plugin, separating a wrong execution location from a misspelling. Each unknown member warns once so repeated reads do not overwhelm the log. The result remains undefined, preserving ordinary feature detection. A developer can give the model the actual API definitions and then test buttons, task access and event handling against them. A plausible function name alone is no longer the most useful clue available during repair.

Examples must agree with the runtime

The change also repairs a contract that could mislead both humans and models. The action hook had declared action as a string even though the runtime passed an action object. The corrected type includes its type field, while the unused optional payload remains to avoid unnecessarily breaking TypeScript references. Three hook examples were corrected, and the AI-oriented prompt now lists recurring mistakes and points to raw types.ts. Packaging still uses a manifest, script and optional interface. The manifest should declare the oldest application version that supports the methods used. A user on a slower release channel cannot infer support in an older client merely because an API appears in current documentation.

A merge is one step before distribution

The source and documentation use the MIT license, allowing people to inspect and adapt their extensions. The evidence here is the merge and the maintainer’s reported automated checks, not an independent measurement of plugin success or proof that every desktop store has shipped a new package. The maintainer records remaining limits: some host methods absent from public types are not suggested, and the warning in a minified production build had not been checked manually. Better diagnostics reduce uncertainty about the origin of a failure. They do not select permissions, review external calls or establish that a task was actually changed. Existing plugins still need checks against execution location, real types and the minimum supported version.
