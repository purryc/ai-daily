CrewAI routes spreadsheet inputs through row tools and records evaluation failures explicitly

A spreadsheet should be more than a URL in a prompt

Version 1.15.38 adds the ability to read spreadsheet URLs supplied in an agent input and use tools across their rows. For developers building list review or enrichment tasks, that is a more explicit data entrance than pasting an entire sheet into a prompt. It does not establish that every private spreadsheet is accessible or that all formats and table sizes were tested. A useful implementation should retain a row identifier and check how blank rows, duplicates and missing values appear in the output. Otherwise a polished summary can conceal an omitted record. The release describes a capability, not a measured guarantee that every row receives a correct result.

Tasks and tools define the work

CrewAI separates an agent’s role, goal, model and tools. A developer can assign a particular job to a specialized agent and pass its result to another step; the available tools are still configured rather than assumed to be unlimited. That organization helps when stages need different context, but it creates another handoff to inspect. A later agent may treat a fluent explanation as verified data. Our interpretation is that spreadsheet workflows benefit from validated fields and preserved original row identifiers, rather than from increasing the number of agents. Delegation, code execution and iteration limits should be deliberate task settings. None of those controls alone establishes that the model’s interpretation is correct.

A default model change changes behavior

The release also changes the default model to gpt-6-luna. If a project relies on an implicit default, upgrading the framework can therefore change behavior without a developer editing the task prompt. Model selection belongs in reproducible configuration, not only in a README. Official guidance supports environment, configuration-file and code-based selection and notes that parameters differ across providers and models. We do not infer a price or performance advantage from the new default. For a workflow handling customer records, an upgrade check should confirm the actual model, credential source, accepted parameters and output schema. A successful API response is not sufficient evidence that the downstream contract still holds.

An error exit must not look like a completed evaluation

The release fixes failed evaluation accounting and non-zero exit behavior when a project script fails. Those signals matter to whatever runs next: an orchestrator that cannot distinguish failure from success may publish a report for work that never completed. CrewAI’s documented structure combines agent crews with conditional flows, so failure needs to survive the handoff between those layers. A practical check would deliberately introduce one invalid input and one tool failure, then compare row-level output, process exit and evaluation records. That check was not performed here. Better failure reporting improves the inspectability of execution; it should not be presented as evidence that the underlying model reasons more accurately.
