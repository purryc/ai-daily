One integration across two organization types

The October 29 release notes introduce a beta with separate usage and cost read endpoints for Claude Console and Enterprise organizations. Older Console and Enterprise reports become legacy but remain supported; this is not an immediate shutdown. Teams maintaining reporting jobs can schedule a migration rather than urgently replace every collector. The new surface feeds a company’s own reporting system with who used a model, how many requests occurred and what they cost over a period. It is an observation interface. Reading a cost total does not restrict the next inference request, and request volume alone does not show whether the underlying work produced a useful result.

Dimensions determine the returned rows

The usage endpoint groups dimensions such as model, workspace, service tier and actor, and supports metric ranking or time ordering. Rows separate their interval, grouping values and metrics. Ungrouped dimensions are null, while empty buckets have no row, so a charting pipeline must handle gaps deliberately rather than assume the API lost records. Up to five ordinary grouping dimensions are supported, with filters independent of grouping. Actor attribution also distinguishes users, service accounts and keys. That lets an administrator ask who generated usage rather than merely which credential authenticated it. The downstream report should preserve the actor type instead of treating machine services and people as interchangeable entries in a ranking.

Cost fields carry billing semantics

The cost endpoint expresses dollar-denominated costs as decimal strings in cents and separates list-price amounts from costs after discounts but before credits. Cost-type and token-type breakdowns help distinguish model consumption from tool charges and can expand the number of returned rows. Usage covered by a Priority Tier commitment may have token usage but zero token cost because the commitment fee is billed separately and is absent from this dataset. Treating every zero as free service would distort allocation. A sensible integration compares a settled period with the existing billing interpretation before using the feed as a team dashboard source. Replacing the URL while retaining old amount parsing is insufficient.

Freshness determines the appropriate monitoring task

The guide says data typically refreshes within four hours and may take twenty-four; late events and reconciliation can revise a month until roughly seven days after it ends. A data_refreshed_at timestamp identifies the snapshot shared across pages. A query spans at most thirty-one days, or one day when using minute buckets. Console access requires administrative credentials; Enterprise requires Analytics API enablement and read:analytics permission. An ordinary inference key does not automatically grant reporting access. These properties suit attribution, periodic comparisons and finance summaries. Near-real-time budget protection needs an appropriate separate control. Migration therefore changes both response handling and the timeliness assumptions of a collector originally built around the legacy interface.
