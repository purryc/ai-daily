Reach an existing deployed resource directly

AWS announced AgentCore CLI 1.0 on October 28. It retains project-oriented development while adding resource command families that address deployed runtimes, harnesses, gateways, memory, identity and payment resources directly by identifier or ARN. Those resources do not first need to be registered in a local project. For someone taking over an existing service, investigation can begin with the actual deployment: inspect it, invoke it or enter an interactive runtime shell without reconstructing a project. Shared region and JSON-output options support both human menu navigation and structured results for scripts. This is a change to terminal workflows and command organization, not a simultaneous first release of every underlying AgentCore service.

Projects still distinguish configuration from owned code

The repository distinguishes two agent forms. A managed harness declares its model, instructions, tools and skills in configuration; a runtime executes code owned by the developer. The project records resource declarations and deployment accounts and regions, while the generated CDK application connects them to infrastructure. Adding a runtime does not implement the business logic: it creates a directory and protocol contract that the developer must satisfy. Development, build and deployment commands then synchronize relevant code settings into configuration. Interactive menus and JSON output are two ways to operate this system, not proof that deployment succeeded. Invocation results, runtime logs and traces help establish whether the intended model and tools actually ran.

Migration changes more than a version number

The migration guide calls for running migrate inside the existing project, rather than changing a version field manually or copying files into another project. CLI v1 actually uses project-format version two, harness configuration moves from JSON to YAML, and evaluations move under the eval command family. Some defaults and semantics also change. Deployment no longer uses the old confirmation flag in the same way, and the previous deployment dry-run option is unavailable. Build synthesizes the project; it does not establish that an update will avoid resource replacement. The generic quickstart still shows some older flags, so upgrades should follow the explicit v1 breaking-changes reference and review affected automation steps individually.

Credentials and service bills remain outside terminal convenience

The current repository requires Node.js version twenty point twelve or later and configured AWS credentials; Python templates also use uv. When an existing execution role is supplied, CDK cannot modify that role’s permissions, leaving the required grants to be configured separately. A unified resource-management experience does not imply that every resource is free or available in every region. AgentCore meters the capabilities used, and runtime compute, code storage, network transfer and model calls can contribute separate costs. For teams, the immediate benefit is a more coherent path through resource discovery, invocation and troubleshooting. Deployment still requires checking the target account, region, identifiers, migrated configuration and ownership of the resulting bills.
