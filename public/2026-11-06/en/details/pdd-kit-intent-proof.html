A requirement can permit the wrong outcome

A requirement saying that only a correct password may produce a token still permits a login system that refuses everybody. PDD Kit’s decision card exposes that ambiguity and asks whether the correct password must also succeed. The person supplies an explicit choice before the agent settles the specification. This is a useful interaction responsibility: a tool can reveal ambiguity without silently deciding the business rule. Similar questions arise in orders and permissions, where a missing successful branch can matter more than another routine happy-path test. The product idea is worth examining at the decision point, before generated implementation volume makes review difficult.

Proof depends on the stated scope

Verus checks specified properties of Rust code statically using solvers rather than adding runtime assertions. Its repository documents a supported subset of Rust and ongoing development. PDD Kit brings that machinery into intent review and generation, but a reviewer still has several separate questions: is the intended behavior complete, is it expressed correctly, and does the implementation satisfy that expression? A strong answer to the last question does not fill gaps in the first two. An omitted account-locking rule or unclear error experience remains a product question even after the stated specification has been successfully verified.

Make trusted components findable

The demonstration distinguishes proof from tests and asks the developer to accept trusted boundaries. External behavior such as database access, password checking and signing does not inherit a proof merely because the core logic passes. Nor does the stated specification guarantee that a query finishes. Keeping those boundaries visible helps later maintenance: after a dependency change, someone should be able to locate the affected assumption and decide what to recheck. A single green completion state would obscure the difference between a proved property and behavior sampled by a test. That distinction matters long after the initial code generation session has ended.

A narrow trial is easier to examine

An initial trial can choose a sensitive flow with known counterexamples and regression cases. Have a domain expert review intent before generating specifications and implementation. Introduce one ambiguous requirement and check whether the decision stage catches it; then change a trusted assumption and see whether the affected promise is easy to locate. This is a proposed trial, not an execution performed here. General commercial availability and pricing were not established. Existing code review and tests remain useful comparisons. The relevant cost includes finding valid defects, completing specifications and maintaining proofs, rather than the length of generated proof files or the number of tests produced.
