One result type for two calling styles

Training scripts often mix synchronous data preparation with asynchronous sampling and training operations. Inconsistent return types make developers remember whether a call has submitted work or still needs another waiting step. Tinker 0.38 standardizes on APIFuture, with explicit adapters for Python concurrency utilities. This changes how developers organize requests rather than changing the model itself. For a team maintaining several experimental scripts, consistency can reduce special cases. It also makes migration more consequential than renaming a method: the code must still request the same work, obtain the right result type and preserve the intended relationships between operations.

Waiting is not the submission switch

The migration guide explicitly says a sampling request is submitted when sample is called. Converting the returned object to a coroutine changes only how the caller waits. Its training example submits forward-backward work and an optimizer step before awaiting both results, preserving their intended pipeline order. This distinction also matters in an experiment dashboard. Displaying “not awaited” as “not started” could mislead someone about remote work already submitted. Logs should distinguish submission, waiting and completion, and cancellation handling should inspect the actual remote state. The release does not establish a general speed improvement from the more consistent interface.

[S89]

Compatibility warnings are temporary

Older async-suffixed methods emit FutureWarning and are scheduled for removal. Client factories also return futures, so code that immediately treats their result as a client needs attention. The migration table distinguishes run management from administrative operations and identifies methods already removed; a blanket compatibility claim would be misleading. PyPI lists Python 3.11 or newer and Apache 2.0 licensing for the SDK. That does not make remote services or model usage free. Pinning a version and retaining a reproducible small task makes changes easier to diagnose than upgrading every experimental environment at once.

Validate migration with countable requests

Start with a fixed small batch and record request counts, ordering and results under the previous version. Migrate one script, covering synchronous calls, asynchronous calls and concurrent sampling. Check for duplicate submission, waiting on the wrong object and replaying work that already started after an error. No training or cost measurement was performed for this article. A cleaner API can still produce slower experiments if a migration accidentally serializes work. The relevant improvement would be less wrapper code and fewer misuse or debugging problems while preserving behavior. Treating the release as an engineering maintenance task is more actionable than interpreting its version number as a capability upgrade.
