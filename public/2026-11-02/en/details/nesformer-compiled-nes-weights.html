Nesformer runs scripted NES games through compiled model weights

ROMs and timed buttons are the inputs

The entry point is a command-line workflow. A developer supplies a compatible NES ROM, chooses a frame limit and schedules Start, direction or jump buttons over particular frame ranges. The program can display frames in a terminal and save an animated GIF or individual PNG files. Those pictures result from executing the game program; they are not successive images improvised from a prose prompt. Timed button scripts make a run repeatable, but they also require preparation and adjustment. Someone who wants to inspect traces and rerun a small experiment has a clearer reason to try it than someone who simply wants responsive retro gaming.

Compiled CPU logic, with graphics outside the model

The project places the 6502 CPU, two kilobytes of working memory and program ROM inside Qwen3.5-compatible weights and Gated DeltaNet state. A compiler computes the weights rather than training them for the task, while rows in the state matrices serve as addressable storage. The model emits an execution trace. A host program uses that trace to draw images, handle controller input and inject interrupts. The graphics and audio processors are therefore outside the weights. This separation matters when interpreting the demonstration: it explores how a model architecture can carry a deterministic circuit, rather than showing that a general conversational model has learned to impersonate an entire console reliably.

A comparison command stops at the first difference

The check command runs the weights alongside a reference CPU and stops at the first differing token; trace exposes the execution records directly. The author reports several layers of validation, including reference-CPU checks against established instruction logs, circuit comparisons and free-running weight traces. These checks cover different instruction counts and game segments, so they should not be collapsed into a claim that every game works. The useful interaction is the inspectable intermediate result. After changing compilation logic or loading another ROM, a short comparison can identify a divergence before someone waits for a long animation and tries to infer the fault from its final picture.

Speed and compatibility define the use case

Compatibility is deliberately narrow: NROM cartridges, official opcodes and code executed from cartridge ROM. Unsupported cases stop, there is no sound, and some graphics behavior is approximate. The author reports overall execution 150–290 times slower than a real NES and roughly twenty-five minutes for a ten-second example; these measurements were not reproduced here. Code and associated documentation use MIT terms, while bundled test ROMs retain their own licenses and commercial ROMs are not supplied. This does not save computation compared with a normal emulator. It saves an interested researcher the work of assembling this particular experiment, exposing weight construction, state inspection and error checking through repeatable commands.
