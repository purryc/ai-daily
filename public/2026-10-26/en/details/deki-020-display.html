An editable scene that reaches the board

Building a tiny touch interface involves moving repeatedly between a desktop layout and what the board actually displays. Deki places the object hierarchy, properties, assets and build controls in one editor. A maker arranges sprites or text, adjusts component values, plays the scene and selects a board for a USB firmware flash. Existing C++ reflection generates property controls from tagged fields, reducing the need to maintain a separate inspector definition. Preview and hardware use the same rendering path, although that does not replace testing touch on the device. The October 24 change concerns the final display output; the earlier October 12 open-source announcement is background rather than this release’s novelty.

Sending a frame at the right moment

A panel updates row by row. Sending a new image midway through that process can put parts of two frames on screen together. The new display path waits for the panel’s refresh signal, or reads its scan position when the board has not wired out that signal. This changes output timing, not the processor. For a canvas too large for fast internal RAM, rendering works in strips before transfer. The maintainer also optimized common drawing work. The reported demonstration results concern two LilyGO boards, and the changelog gives the AMOLED panel’s actual refresh as about 59.6 Hz. That is not a promise that arbitrary scenes or newly configured screens will reach the same rate.

Physical size changes a touch target

The update also addresses the hand meeting the interface. Lists no longer jump when a swipe begins, and horizontal scrolling follows the finger. A board definition can provide the screen diagonal, allowing the runtime to derive pixel density and make a layout aware of physical size. This information comes from the board description; no sensor measures the glass, and an absent value remains unknown. The new deki-display library covers several LCD and AMOLED controllers and common capacitive or resistive touch controllers. The maintainer explicitly distinguishes parameter checks from physical validation: newly added configurations were compared against an existing library but have not all run on actual boards. Panel wiring and touch orientation still require checking.

Update the packages as well as the editor

A release label did not initially mean a usable download. The changelog says the Windows archives for 0.20.0 and 0.20.1 failed to build; 0.20.2 restored downloads. Version 0.20.3 then addressed Tactility loading and a text-box hang. Existing projects must update their packages, and older copied LilyGO definitions need their own update to adopt the display library. LovyanGFX remains available for unsupported panels. For a personal prototype, this reduces the back-and-forth between handwritten display integration and scene editing. For a device intended for others, the relevant check remains its actual combination of input, assets, memory and screen, rather than the frame rate of someone else’s demonstration.
