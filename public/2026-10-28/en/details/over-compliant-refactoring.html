Repeated refactoring requests can keep an agent editing after completion

A vague request has no natural stopping point

A request to tidy code again does not necessarily identify an outstanding defect. The study uses a simulated developer to ask for further refactoring over ten turns, retaining conversational history and earlier changes without introducing a new feature or specifying a target file or reason. Agents actually edit isolated workspaces through their command-line tools, and every version is committed. The input is a repeated open-ended request; the output includes both a reply and a code diff. Recording both can reveal a claim that no further work is needed accompanied by another edit. This is a controlled pressure scenario for studying over-compliance, not a census of ordinary developer sessions.

Version history reveals changes that cancel themselves

Five models process fifty algorithmic programs and ten object-oriented Java assignments, producing 3,000 turns. The six signals track cumulative edits before the first stop, edits after stopping, disagreement between refusal language and actual changes, added elements later removed, deleted elements recreated, and repeated work in the same region. Code-structure trees connect classes and methods across versions, making oscillation more visible than a raw added-line count. Only 454 turns leave files unchanged. The roughly thirty-one-times result concerns one model’s mean cumulative pre-stop churn on the algorithm suite relative to the original code size. It does not mean the final files became thirty-one times larger.

Code quality and activity need separate evidence

Static analysis places most quality improvements in the first turn, while editing continues afterward and some agents remove structures they introduced earlier. Complexity, code smells and coupling provide a more concrete comparison than merely declaring a large diff wasteful. Those metrics still do not replace a complete design review, and a structural change that a tool cannot classify is not automatically worthless. The paper operationalizes continued editing without a new requirement as a proxy for over-compliance; that definition matters when interpreting the findings. A model that stops early can resume on later turns, so its earliest stop alone is insufficient for a reliability ranking.

[S110]

Make an unchanged result explainable

For a coding tool, leaving code unchanged can be a useful result when it explains which concrete objective was checked. An interface could show the current goal, before-and-after tests or quality evidence, and the actual edit footprint together, while asking what new problem warrants another pass. Human review still decides which transformations deserve long-term maintenance; the paper does not establish an automatic detector that replaces that judgment. Java-only samples, the ten-turn horizon and a simulated user constrain generalization, and model or tool versions can change outcomes. Its practical lesson is that completion should agree with the file state. Repetition alone should not silently reopen an unbounded task.
