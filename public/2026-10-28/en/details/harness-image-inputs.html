Sending the visible problem to the agent

A developer reporting a layout problem often has both an instruction and a screenshot. The picture may reveal overlap, spacing or a state that is difficult to describe precisely. HarnessAgent now allows those inputs to travel together in a user message instead of requiring a different image handoff for each agent integration. That is useful for an attach-and-revise interface or a workflow passing browser observations to a coding agent. The image alone does not supply a DOM node, a source-file location or the intended design constraints, however. An application still needs to organize that surrounding context so the agent can connect what is visible with what it is allowed to change.

The common part is the message shape

The API uses a content array containing text and file parts, with an image MIME type and the file data. The announcement demonstrates a Codex session returning a short description, and lists ten adapters with image support. Interpretation remains the responsibility of the underlying vision model. For a team maintaining several agent choices, the common message shape can reduce duplicated upload and message-construction code. It does not standardize whether a model reads small labels correctly or notices an obscured control. The meaningful comparison is the same screenshot and task across the chosen adapters, while keeping the surrounding instructions consistent. The documented example establishes the input path, not a comparative visual-quality result.

The image enters a managed task

An image request still runs inside a managed session. HarnessAgent can return a completed result or stream incremental output, and its examples clean up both the agent session and sandbox. Credentials, model selection and error handling remain integration work. Lifecycle callbacks expose calls and tool activity, but the documentation says callback errors do not alter execution. A logging callback is therefore a poor substitute for an approval boundary. Adding a convenient screenshot attachment should not silently widen file or network permissions. The person using the finished application still needs to understand whether the next step is a proposed change, an applied edit or simply a description of the supplied picture.

Less integration code, the same page-specific review

Compared with separate attachment paths for each agent, this update mainly removes branching in the adapter layer. A shared upload component and task record become easier to retain while changing the backend. A product already using one well-integrated agent may gain less from migrating. Review still needs to inspect the actual page and changed files, including states absent from the screenshot; a persuasive description does not prove a correct edit. Costs and input limits depend on the selected service rather than a universal HarnessAgent tariff. This is also distinct from the earlier steering update: changing guidance during execution and adding image inputs solve different parts of an agent application.
