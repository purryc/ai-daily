Retain something that can be run again

PyRUA-REAL studies how coding agents preserve physical trial experience as memory and executable skills. Execution supplies observations, diagnosis informs a revision, and later exploration can reuse what was learned. This differs from making a fresh model decision at every step, but a retained program does not automatically generalize. The paper reports physical-robot and RoboDojo simulation evaluations separately. Their task sets and results should not be combined into a product reliability number, particularly when development attempts, resets and assistance shape what the system eventually learns.

Feedback needs to expose the cause

The research examples use images, depth and gripper records to expose detector errors and grasps that close in empty space. Better feedback can therefore change the direction of code repair. Another reviewing agent is not necessarily faster; revisiting the task approach may help more than another local patch. A practical implementation should retain object arrangement, action, sensor evidence and human assistance alongside a failure label. Otherwise, apparent improvement may come from an easier starting condition rather than a more capable program. This is a lesson about diagnosable execution, not proof that adding logs guarantees success.

Contact tasks show where online help remains

Precise cable insertion remains an example where online assistance can still be needed. That exception suggests a useful deployment boundary: package stable actions as programs while leaving uncovered situations a stop or takeover path. A small validation retains the known success case, changes placement or requirements, and checks whether the program recognizes its limits and who must recover it. Hardware, task selection and sample size constrain extrapolation. The work offers a research framework for reusable behavior, not a robot service demonstrated to handle arbitrary customer environments.
