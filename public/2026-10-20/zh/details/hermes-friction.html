一条新报告：工作仍在执行，用户却失去反馈

Hermes Desktop 面向把文件、浏览器和工具任务交给同一代理的用户：在原生窗口里选模型、发起对话，查看工具活动、文件与并排预览；它与 CLI、gateway 共享配置、会话、技能和记忆。10月19日新开的 #141485 报告了一个具体落差：原生 Windows 11 上，代理执行工具时，窗口反复冻结，后端进程却没有退出。作者给出的环境是 Hermes 0.22.2、指定代码提交、9月17日打包桌面构建和 Python 3.14.7；不能把此组合代表所有当前安装。帖子创建于10月19日10:01:40 UTC，早于本期24小时窗口，故列为近三日补充；日志仅写当地10月19日，时区未知。本期新增的是可追溯使用观察，不是Hermes重新发布，也不是本刊实测。

操作链与失败：状态读取和工具执行挤在一起

正常操作链是用户打开现有安装、在对话中交代任务，代理选择工具，桌面持续显示进度，再把结果交回供人核对。此例工具包含 computer_use 的 Windows UI Automation 枚举，以及一次寻找当天文档的整盘终端扫描。作者贴出的后端日志出现约37至45秒的事件循环停顿，状态和消息读取请求超时；这是同一台机器的诊断线索，没有用户总体分母。

[S13]

进度反馈消失，用户无法判断下一步

问题的交互后果比“回答慢”更具体：当绘制聊天界面所需的状态和会话消息也排队时，用户看见旋转指示却拿不到可靠进度，难以判断应等待、取消还是重复发送。报告同时提供充足剩余内存、未检测到OOM的记录，提醒排查不要直接归因为模型太大；但这些记录也不能单独证明GIL就是唯一根因。

[S13]

现有控制与采用门槛：绕开触发器不等于修复

作者的临时办法是关闭默认 computer_use，并用工具调用前的hook阻止从盘符根目录开始递归搜索；这会缩小自动化任务范围，而不是证明底层已修。帖子唯一回复把它关联到既有资源消耗tracker，API显示回复者关联身份为NONE，不能写成维护者确认或修复承诺。官方0.22.2发行说明另说0.22.1曾从错误提交构建，0.22.2恢复预期发行线，并提醒某些经过0.22.1 gateway的会话不能删除；它未声称解决本次运行中冻结。

安装渠道与替代操作链

安装迁移也有实际边界：README要求按产物所属渠道更新，Store、App Installer、macOS包与源码安装不同，hermes update不能改写捆绑包。相比直接手工在目标文件夹查找再提交明确文件，代理整盘探索省去的是前期定位动作，却扩大执行范围。相比同产品CLI，GUI更集中呈现预览和设置；共享后端意味着换界面不能被宣传为已证实的根治办法。

产品判断：可接管能力必须在重任务中仍然可达

对产品经理，这个案例支持的是一个待验证的设计命题：长任务的控制通道应与重工具的执行压力分开，界面至少应保留最后一次可靠状态、正在运行的工具、已持续多久以及哪些操作已经获确认。不能在没有证据时宣称当前产品具备独立取消、完整撤销或自动恢复。最小验证可以在隔离测试机上，对比限定目录查找与整盘查找、启用和禁用computer_use的同一任务，记录状态接口响应、取消响应和最终产物是否重复；固定版本并保留失败轨迹。若当前稳定安装无法复现，或阻塞来源不同，应下调这一推断，而非沿用旧结论。使用者在意能否接管，团队决策者在意支持负担和版本一致性，模型与托管成本本次未核价。配图为插件作者公开的真实Linux桌面会话，可辨认会话分组、运行任务与文件栏；不是该Windows故障截图，也不证明任务完成率。
