谁用与变化

Exa 三点零面向把网页检索放入助手和业务流程的开发者，新增低价 Lite 搜索，并让 Dynamic Highlights 正式可用。发布价为 Lite 每千次四美元、Auto 每千次七美元；更广的数据覆盖包含商品、地点及动态信息。对 PM 而言，具体任务可以限定为回答一个门店的营业时间并附原始链接，而不是笼统追求更聪明的搜索。发布页仅标十月十九日，按近三日回看处理；所有排行和 token 节省都是厂商声明，本轮未复跑。

API 到用户答案

现有官方示例通过 search 发送查询，并请求 highlights；调用者得到标题、原始 URL 和摘要片段，再把证据传给回答模型。这个链条至少包含查询组织、返回结果选择、答案生成和向用户展示证据四个责任点。PM 推断：应用不应把一句流畅答案当成检索已成功，尤其地址相近、名称重复的门店。更合理的状态是候选地点待确认、证据足够、信息冲突和无可用结果；这些是产品设计建议，并非声称 Exa 已提供完整终端界面。

[S23]

便宜模式的真实限制

当前 API 参考明确 Lite 只使用缓存内容、不现场抓取，且只接受列出的参数，其他参数会被拒绝。它支持域名和发布日期筛选，但“有日期筛选”不等于内容刚刚更新。故不能把 Lite 描述成廉价实时网络。对变化缓慢的背景事实，缓存或许足够；对今天临时停业、售罄或赛事分数，PM 应安排更新鲜的证据或明确不确定性。API 文档列出的错误包括鉴权、额度和限流类状态；本轮没有建立密钥，也未发起收费调用。

[S22]

替代路径与验证

替代方案先是现有 Auto 路径，或让用户直接检查商家官方页面；若应用已有可靠的领域数据源，也不必为所有问题增加通用检索。PM 假设是把稳定查询交给 Lite，把不确定或高时效查询升级，可能降低总成本，但这只是待验证的路由设计。用同一组带时间标签的问题比较正确出处率、答案过期率、升级重试比例、总延迟与最终每个正确回答成本；再人工核查被 highlights 压缩掉的例外条件。若便宜请求导致更多重试与错误解释，其单次报价优势就不足以支持迁移。
