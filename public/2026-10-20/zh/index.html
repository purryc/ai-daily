SpeakON Agent / 操作与判断

输入入口：先接住想法

旧操作链是解锁手机、找到笔记或邮件、打字整理、复制到任务工具，再手工设提醒。官方展示的新入口有软件键盘与磁吸硬件按钮：选中SpeakON键盘，或按住设备按钮说话；当前有文本框时，整理后的文字进入所在应用；没有活动文本框时，内容保存为可编辑Note。用户仍需读回输出，确认人名、日期与否定词没有在去口头语和改写时被改变。离线能力是录音与之后同步，处理及在线AI功能需要网络；不能把锁屏捕捉或离线保存写成所有Agent动作都能离线完成。产品价值发生在捕捉和整理之间，跨应用执行是后续独立步骤。

[S02] [S03]

从Note到Task：动作不能混为一谈

公告用一个具体例子解释Agent：把团队套餐改成年付的想法存下来，下周二提醒复查，并给Alex准备后续邮件。系统先生成Note，再把提醒和邮件整理为Task中的建议Actions；用户审阅并确认后，创建提醒、准备邮件。商店说明又列出发送邮件或Slack消息、创建日历事件等能力。两者不是同一个权限强度：准备草稿与发送消息应分别呈现，不能从公告中的草稿案例推断默认自动发送。产品经理要检查确认画面是否具体列出收件人、内容、执行时间和目标账户，而不是只提供一个笼统的“继续”。这些字段是否完整可见尚未实测，不能替厂商补齐。

SpeakON Agent / 操作与判断

状态与失败：停止不等于撤销

商店发行说明列出Live Activity和通知来展示任务进度，也记录修复某些场景下键盘卡在加载状态的问题；这是开发者发行声明，不是本次复现结果。官方Data Controls明确允许随时停止活动Agent任务、断开连接服务，但停止未来访问不一定撤销已经在第三方完成的动作。比如提醒创建成功、邮件发送失败，用户需要知道哪一步已完成，再决定是否重试，避免重复提醒或重复发送。我们未核实它是否提供逐动作回执、幂等重试或跨服务撤销。设计洞察是把任务进度和外部副作用拆开显示：生成完成、待批准、执行中、部分成功、已停止，各状态应有不同含义；这是本刊建议，不是新增功能清单。

[S03] [S04]

数据路径与迁移成本

官网称用户可以关闭Cloud Sync，但Data Controls进一步说明，关闭跨设备保留不影响完成转写、编辑或笔记生成所必需的临时处理，词典与账户偏好仍可能同步。这意味着“不同步”不能解读为“完全本地推理”。连接服务只应取得所授权且完成任务需要的内容，用户可在相应设置断开。迁移成本不只是购买按钮：还包括启用键盘、管理网络访问、配对设备、建立专业词典、核对工作账户，以及训练使用者区分文本输出与真实外部动作。对受约束团队，先用无敏感内容验证权限与输出路径比把现有客户邮件全部接入更可审查；本期没有进行账户连接或真实发送。

SpeakON Agent / 操作与判断

产品判断：把声音保留为意图证据

此产品最值得观察的不是“用声音替换键盘”的口号，而是Note作为可编辑中间物的作用。直接从原始口述跳到执行，会把省略、犹豫和临时想法变成难以回退的承诺；先保留想法、再形成任务，让用户在批准前有机会修正含义。跨端连续性也不应只指能看到同一篇笔记：手机的捕捉状态、云端处理状态与第三方的完成状态需要共同解释。我们的价值假设是，可审阅的中间物能减少遗漏的后续工作，同时保留负责人判断。现有材料足以确认厂商提供这条产品叙事和部分接口描述，尚不足以证明真实完成率、节省时长或长期留存；这些结果留待使用研究。

MirrorShip MIP / 操作与判断

从自然语言到可检查的结果

官方页面的销售与毛利分析演示依次展示：用户提问，抽取指标、时间和区域，召回已认证语义视图，绑定净销售额定义并生成SQL，校验权限、数据新鲜度与口径，最后交付结果及Evidence。这里能看到正在检索、已锁定资产、执行前校验和查询过程等状态；页面中的销售金额、匹配比例和执行时间只是演示数值，不能写成性能证据。原来分析师手工找表、确认公式、写Join再与财务报表对账的链条，被拆成可复用定义与本次查询选择。MirrorData承担数据访问，MirrorMind组织语义及上下文，MirrorPilot提供问数入口，MirrorControl描述贯穿过程的治理。

失败不会因出现绿色勾而消失

镜舟自己的技术文章给出了很具体的反证边界：订单和明细连接后，订单金额可能按明细数重复累计；主键、唯一键和关系声明不会替用户清洗底表。EXPLAIN INLINE能显示展开后的SQL，但不等于查询审计；PRIVATE控制语义元素可见性，也不自动替代底层行列授权。因此用户纠错需要逐层看意图映射、视图公式、Join粒度与原始数据，而不是反复改一句提示词。官方产品页虽提到审批、Trace、成本和反馈，本次未取得可实操的取消查询、撤销业务动作或异常重试流程，不能据此承诺。对决策者而言，能够解释错在哪里，比一句“可信答案”更值得在试用中核查。

MirrorShip MIP / 操作与判断

替代方案与迁移成本

对已经拥有规范SQL报表的团队，人工分析加共享指标文档仍是有效替代；对于只缺搜索说明文档的任务，检索增强知识库也可能足够。MIP针对的是定义要参与计算、且多套Agent需要共享定义的情形，不能用厂商材料证明它胜过所有ChatBI。切换成本不只是换聊天窗口：需要指定指标所有者、整理维度映射、确认历史口径、生效日期和访问路径，再验证现有报表与新入口是否一致。官方允许企业保留已有Agent入口，降低重做前端的必要性；但适配工作、报价、运行额度和目标环境支持仍需逐项确认。这里的采用门槛是把分散的业务知识变为可维护资产，不能把这部分劳动宣传为自动消失。

产品经理要验证的变化

最小试点可以选两套现有报表里经常对不齐的净销售额指标，保留人工确认的参考查询，加入退款、跨区门店和明细重复三类边界样本。观察的不是聊天回答是否流畅，而是系统能否把差异定位到定义、时间范围或聚合粒度，并让业务负责人完成更正。若接入后仍需每个Agent另写一套公式，或分析师无法追溯数据与语义版本，共享语义层的核心价值假设就被削弱。还应比较业务用户从发现差异到取得可核验解释的步骤数，而不是沿用官网演示秒数。这个产品的HCI机会在于把后台治理状态带到提问者看得懂的位置；公开演示说明了方向，真实团队能否据此降低对账负担仍未得到独立验证。

先选择任务再选择板卡

SL使用Astra SL2619与1 TOPS Torq/Coral NPU，面向Linux端的视觉、音频及小模型任务；SR公开规格使用400 GOPS NPU并聚焦资源紧张的感知系统。两种板卡不能混用算力规格，NPU数字也不能当作整板耗电。对于电池设备，摄像头、无线与显示器都会改变系统预算。PM首先要限定持续监听、间歇识别或机器人视觉任务，并要求工程团队解释模型在CPU和NPU之间怎样分配，而不是只比较TOPS。

验证体验而非证明概念

最小验证可用同一量化模型与固定输入，先测离线准确性，再在真实传感器、连接和待机策略下测整机能耗、唤醒与响应。只有输入输出相同，才能判断工具链一致性是否降低迁移工作。若新模型必须改写大量算子，或加上相机无线后超出电池预算，就应推翻“轻松常开”的判断。多模态机会是把语音、视觉与环境感知接在设备端，减少云往返；何时上传、如何告知持续感知、何时允许人工接管，仍是终端产品需要设计的控制，不是板卡公告已经解决的功能。 对采用门槛，还需区分样机团队与量产团队：前者要尽快证明传感器输入和模型输出连通，后者要确认接口、物料、系统更新与维护周期。可以复用模型不代表可以直接复用整机设计；开发板上的扩展模块、调试线和实验室电源都需要在量产方案中重新安排。这个差异会改变购买开发板后的真正项目预算。

LiteRT Tensor API / SAM 2 Web demo

为什么增加原生编写入口
