Actual increment: a new context object, not a renamed chat

Figma announced Specs in open beta on October15, with a staged rollout to paid plans. An October19 Product Hunt appearance is a discovery signal, not the original launch. There is a concrete increment: a document can live on the canvas, reference design objects and FigJam material, and host collaboration around shared intent. This should be distinguished from the agent's earlier ability to produce text. The likely users maintain requirements, designs and implementation constraints together. A useful job is handing over a checkout change with its exception states, design references and implementation decisions intact, rather than merely producing a longer product requirements document.

Workflow: from design decisions to implementation and back

Users can create a Spec from the toolbar or by pressing D, or import Markdown. They can add requirements and relevant frames, bring code context through a connector, then pass the resulting link to a coding agent connected through Figma MCP. The documented direction is bidirectional: design can inform a specification, specifications can guide code layers, and later changes can return to the document. Product inference: handoff should explicitly separate agreed decisions from open questions. Rich references do not mean the team has converged. A comment asking where cancellation should return the user must not silently become a definitive behavior merely because generated prose sounds confident.

State, access and friction: a visible document does not guarantee equal access

The help page requires edit access and explains that staged availability can differ among teammates. Direct writing does not consume agent credits; using the agent does. The document container should therefore not be conflated with unlimited AI generation. On October16, a user requested a centralized Spec library, organization and a pinned floating view to reduce navigation work in large design files. Figma support said the suggestions had been passed to the team. The forum's solved label does not establish that those enhancements shipped. This is a specific signal that proximity to a design and findability across a large file are different problems. It remains one user's request, not a prevalence measurement.

Alternatives and a falsifiable test: shared context should reduce stale implementation

Conventional alternatives are a PRD in a document tool with design links, or repository Markdown reviewed alongside code. Specs' hypothesis is less copying, repeated explanation and tool switching, balanced against maintaining a shared understanding of which document and design states remain valid. Compare the same feature, including success, empty and error states, using a conventional handoff and Specs. Change one constraint midway and count stale implementations, engineering questions, lost comments and rework time. Fewer outdated implementations would be stronger evidence than a faster first draft. Record which document version and references the agent actually read; accessible links do not prove semantic understanding. This review checked documentation and first-person feedback, without exercising an account workflow.
