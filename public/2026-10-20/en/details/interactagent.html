Task, execution and feedback

InteractAgent takes scene images and a goal, plans atomic actions, and sends them to a frozen MotionLLM that generates virtual human trajectories. Rendered results support decisions to continue, redo or replan; memory across attempts informs later plans. This is virtual human-scene interaction, not physical robot control. The paper’s main planner and evaluator use GPT-4o. Executor sensitivity to wording and geometric precision remain limitations. [INTERACTAGENT1]

Reproduction boundaries

The author repository is public, but practical scripts default to qwen-vl-max rather than the paper’s principal backbone. Setup requires Python 3.10, Qwen API access, separately supplied MotionLLM and Gemma weights, and human-model assets. Training-free does not mean dependency-free. The repository labels itself WACV 2027; conference acceptance was not independently verified, and no top-level code license was found in the reviewed listing. Reading code does not reproduce the reported results. [INTERACTAGENT2]

Product analysis: make each failure inspectable

PM analysis: animation previsualization, virtual exhibitions and synthetic activity sequences are plausible first uses. A designer can specify a bounded goal and inspect each step. The valuable interface is not a longer reflection narrative; it is a connection between a diagnosed failure and the specific time, object and trajectory changed in the next attempt. I would retain the original plan, generated motion and revision side by side, allow accepted segments to be locked, and let the user replace one action or change the goal. Otherwise a global revision could improve sitting while damaging an earlier walking segment. Sharing a backbone between planner and evaluator also motivates an independent check: both could accept the same visual misunderstanding. Geometry checks or human review should test cases such as feet passing through furniture instead of relying only on another favorable model judgment. These are review recommendations, not claimed editor features or physical guarantees.

Alternatives and adoption: evaluate the final usable sequence

The alternatives are keyframe editing, assembling motion-library clips, or generation with explicit scene geometry constraints. A fixed action may be more predictable through manual composition; open-ended sequences are where reflection deserves comparison. I would compare single-pass generation, step-level feedback and memory-assisted feedback on identical scenes and goals, holding model access, retry budget and acceptance rules constant. Besides completion, measure penetration severity, API expense per usable minute, render time, animator correction time and the proportion still unfinished at the retry limit. If retries improve average success while a few difficult tasks consume unbounded resources, the product should return the failed segment for editing. Adoption should pin code and model versions and record paper and repository configurations separately. If those configurations cannot produce comparable outcomes, this remains an experimental authoring aid rather than evidence for a production animation service. A demonstration video is useful for understanding the interaction, but cannot establish the cost of producing an acceptable final sequence.
