Keeping the working state after an answer

A document assistant is straightforward on its first turn: receive material, send a request and display an answer. The integration becomes more demanding when the next step queries a database, reads a file or revises the same deliverable. Kimi K3.1 Pro requires the application to retain the complete assistant message returned by its API for subsequent turns, including the working state behind the displayed answer. Its million-token context offers room for more material without deciding which version is authoritative. Outdated requirements and contradictory logs still need selection. The official announcement is dated October 23, while full model weights are promised by November 4; API access and self-hosting availability are separate stages.

The model proposes a call; the application executes it

Developers describe each tool through a JSON schema specifying its purpose and arguments. The model selects a tool and proposes parameters; application code performs the operation and returns a result tied to the call identifier. That division leaves a concrete place for product controls. Reading project status might proceed immediately, while changing a shared record could first show the target and proposed edit to its owner. A stronger model does not automatically gain broader permissions. If a connection fails after a write succeeds but before the result reaches the model, the application must check actual state before repeating it. The documented loop does not supply every external system with undo, approval or duplicate-write protection.

Adjust effort without discarding history

Thinking cannot be disabled. The reasoning_effort field offers low, high and the default max setting; a K2 integration should remove its older thinking configuration when migrating. Replacing the model name alone is therefore insufficient. An interactive lookup can use a smaller reasoning budget as one latency choice, while a complicated batch job needs a comparison of completed work and consumption. The highest setting is not automatically the best economic choice. Streaming separates reasoning from the final answer, and structured output should be parsed from final content only. Treating progress text as the business result can put the wrong material into a database even when the request itself is syntactically valid.

Repeated material has a reuse interval

Context caching reuses an identical prefix. Stable rules, tool definitions and reference material belong before changing questions and tool results; inserting a fresh timestamp at the front prevents reuse beyond that point. The default lifetime is five minutes, with a one-hour option and a separate write charge. A workflow paused for human approval consequently has different reuse patterns from a continuous loop. Caches are organization-scoped, expire after inactivity and cannot be manually cleared; they are not a user-managed long-term memory store. API billing is usage-based and distinct from membership or Kimi Code. The quickstart also warns that built-in web search is being updated and is not recommended for near-term production use, leaving retrieval an explicit integration responsibility.
