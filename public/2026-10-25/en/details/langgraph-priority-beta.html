Express differences in a shared queue as application policy

One agent service may handle interactive questions, background preparation and long jobs from several accounts. Treating them identically can leave a person waiting for a short answer behind unattended work. The new Priority object lets a deployment return scheduling settings from a Python policy rather than placing a request for urgency inside a model prompt. The callback receives identity, permission and task context from which it can choose priority and a fairness group. This is a service-policy interface, not a model deciding whose work matters most. The application team still defines commercial rules, capacity budgets and how higher-priority work should coexist with other users.

Settings are assigned initially and retained on the thread

The server invokes the assignment function when a thread first runs without existing settings, then stores its result on that thread for later runs. Context includes user permissions, thread, assistant and graph identifiers, relevant metadata and a cron identifier when applicable. A run that creates a thread can supply no thread ID, so policies must handle missing values. The context object is frozen rather than an editable carrier. Because assignment is not recomputed on every turn, an account upgrade or permission change should not be assumed to reclassify an existing thread immediately. A product advertising queue benefits needs to explain when current work adopts a changed policy.

Priority and fairness groups express different choices

Priority ranges from minus five to five, with five running first. A fairness group is a nonempty string, and fairness weight ranges from one to one hundred. Omitted values default to zero, default and one; returning None also selects defaults. The group is stored unencrypted, so it should be an opaque internal identifier rather than a name or email address. An application might distinguish interactive from background work while grouping shared capacity by account. The release does not promise waiting times for all workloads. These fields add no compute capacity, and assigning every request a high number cannot resolve congestion or demonstrate continued progress for lower-priority work.

The server must understand the configuration

The companion CLI accepts a priority path in langgraph.json, rewrites it to the image location during packaging and passes it to the development server. The target must be a Python object; a primarily Node.js project cannot point directly to a JavaScript or TypeScript callback. An older server can ignore the section, so a successful build alone does not show the policy is active. The interface remains beta. For a team already maintaining an external queue, this may remove some surrounding assignment code, but replacing an existing scheduler depends on actual concurrency, cancellation, recovery and waiting behavior rather than the presence of a configuration field.
