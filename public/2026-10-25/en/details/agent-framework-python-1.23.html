Authentication does not by itself identify the owner of stored state

A web agent can require sign-in while still storing different people’s snapshots, paused work and approval state without a meaningful ownership scope. AG-UI thread IDs belong to the client and correlate conversations; they should not define authorization. Version 1.23.0 requires each endpoint to choose an ownership mode: the new authorization_scope_resolver, an existing snapshot_scope_resolver, or an explicit single_user declaration. The resolver derives a stable nonempty scope from authenticated request context before protected state is accessed or streaming begins. The application still decides whether that scope represents a person, team or tenant. The SDK cannot infer an organization’s collaboration policy merely from successful authentication.

Local demonstrations and shared deployments need different configurations

A FastAPI resolver can reuse dependencies, request data, cookies or an existing security context, so developers do not need a new login screen. It carries the established identity scope through snapshots, internal sessions, checkpoints, detached runs and approval storage. A genuinely single-user application can declare single_user and receive an opaque scope for that endpoint registration, avoiding collisions between identical route paths in one process. That scope lasts only for the registration’s lifetime. Applications needing continuity across restarts or shared storage must supply their own resolver. Previously unscoped registrations fail after upgrading; this is an explicit migration requirement rather than an inferred default tenant.

Every released tool result must enter conversation history

A separate fix addresses tool approvals submitted across several requests. A user may approve one pending call and approve another later; middleware then releases both together. Previously both results could stream successfully while the saved snapshot retained only the result associated with the final request. The next user turn replayed two calls with one result missing. The updated runner records each result as it streams and merges missing entries into the snapshot in call order. It does not change approval authority or introduce automatic approval. It aligns the successful events the frontend displays with the history the application actually saves and restores.

Recovery first determines who owns the connection

The MCP 2.x migration also clarifies connection ownership. When an application supplies a Client or ClientSession, the framework does not own closing or rebuilding it. An older recovery path nevertheless announced reconnection and issued another request against the same ended object. Definitive loss now returns an actionable error asking the caller for a replacement, while framework-owned connections keep their existing recovery behavior. That makes an unanswered tool operation easier to diagnose without suggesting a reconnection occurred when none did. Adopters need to identify who owns their existing clients and whether authorization scopes and approval snapshots remain consistent across a real application restart. Replacing a connection does not itself authorize a previously restricted business operation.
