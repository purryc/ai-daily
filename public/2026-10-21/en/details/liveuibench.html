01 · Control and recovery

The hard part of a dynamically generated interface often appears on the second operation. After creating an expense, task or shopping record, a user may want to change only its date and then return to inspect it. If regenerating the interface loses record identity, the page can still look complete while duplicating data, changing the wrong row or displaying an old value. LiveUIBench evaluates that continuing chain through independent backend reads and stable identifiers. Its accompanying LiveUIAgent explores a shared runtime that preserves application identity and records, shifting the agent from a one-time code producer toward an ongoing organizer of application behavior. That role brings a stronger state-management obligation. A conversational acknowledgment that something was changed cannot substitute for checking the actual record.

02 · Mechanism and limits

The paper includes 500 tasks, 2, 408 episodes and 10, 590 assertions across nine AppWorld services. Three levels of success must remain distinct: opening the application, satisfying an individual assertion and completing the whole workflow. The authors report that Grok 4.6 opened 491 of 500 tasks while completing 19.6 percent of full workflows; GPT 5.6 Sol opened 483 and completed 11.4 percent. Those are results in the benchmark’s service environments, not measurements on real Amazon or Gmail accounts. Nor can a higher assertion pass rate replace the lower workflow completion rate, because the units answer different questions. For product planning, the valuable follow-up is identifying the failing state transition: initial submission, revision of the intended record, persistence, or the interface shown when the person returns.

03 · Acceptance and alternatives

Manual alternatives include fixed forms backed by a database, spreadsheets, or regenerating code followed by a human inspection of data migration. These may be less flexible, but they often make it clear where a record lives, what changed and how to undo it. To improve on those alternatives, an agent-as-app system must keep identifiers, submission feedback, revision scope and later displayed state aligned.

04 · Acceptance and alternatives

A practical test changes exactly one field, confirms that other fields and the record identifier remain unchanged, and then introduces similar records, repeated revisions and a backend write whose response never reaches the interface. The study’s bounded tasks and short histories do not demonstrate long-term durability or production deployment readiness, and commercial availability was not established. The falsifiable product judgment is whether the user can return and trust that the intended record was changed. If every revision still requires a manual investigation of which row was affected, convenient interface generation has not yet become a dependable application experience.
