A successful response can still contain a refusal

A successful HTTP request is not the same as completed work. A model can return refusal content while an execution chain ends normally, leaving a parent agent or interface with an apparently successful subtask that produced nothing useful. DeepAgents 0.7.33 introduces default refusal middleware that turns this situation into an explicit ModelRefusalError. Declarative and general-purpose subagents receive the behavior as well. For applications expecting a file, an analysis or structured output, the status no longer depends only on whether the transport raised an exception. It can also reflect whether the model supplied an answer that the workflow could actually use.

A subtask error needs an explicit boundary

A refusing subagent reports that condition to its parent through the task result, including refusal content blocks and structured refusal forms, while other errors retain their error path. Async execution has corresponding handling. One important boundary is that state updates may be unavailable after the child raises: files and todos are not returned as if they had been successfully committed. A parent must not invent those missing deliverables. Existing model-fallback middleware has its own ordering, but that should not be advertised as a way to evade every refusal. The application needs to decide what happens next from the task and its permissions rather than optimizing solely for a green completion state.

Which message follows the summary

Version 0.7.34 also repairs the retained-history boundary after context compaction. If earlier messages are summarized and the first remaining full message is stored only as an array index, subsequent edits to earlier history can shift that index and skip content that should remain. The new implementation records the stable ID of the first retained message and resolves the boundary from it. Old records or missing IDs still fall back to the previous index. This is compatibility with history editing, not unlimited memory. It also does not automatically remove later-deleted material from an existing summary; an interface promising deletion must separately address the relationship between summaries and stored messages.

Status words should match the underlying event

Both changes affect information an agent product shows to a person. Completed, refused, compacted and retained should not merely describe whether an internal function returned normally. A task-list interface needs to preserve the failure reason and identify deliverables it has not received. A history interface needs to know where full messages resume after a summary. Otherwise users may continue from an empty result or assume that a skipped constraint was read. This account relies on release and implementation records, not a long-running execution test. Summary completeness and the clarity of refusal messaging still depend on the application built above the SDK; the directly usable improvement is more explicit error and boundary semantics.
