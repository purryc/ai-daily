Separate task requirements from the running program

PyRUA-REAL receives a task goal and descriptions of the variations the program must handle. A researcher agent chooses approaches and stopping conditions, while an engineer implements, executes and diagnoses programs. Foundation-model parameters stay fixed; learning persists through code, skills and records. The physical setup uses two Franka Research 3 arms, Robotiq-85 grippers, a head-mounted ZED Mini and wrist-mounted RealSense D405 cameras. These are sensing and manipulation components of the experiment, not newly invented sensors. The resulting artifact can run independently of the development agents, continuing to use live observations through ordinary perception and control logic rather than consulting a language model before every action.

A failed check can be a measurement problem

The diagnostic examples distinguish physical failure from faulty measurement. In tic-tac-toe, a detector merged touching rings and rejected a correct placement. A stacking case used an unintended camera view, producing misleading return-error estimates. Correcting those checks changes the recorded result without necessarily improving physical motion. This distinction matters for any product that asks an agent to revise behavior from feedback: a failure label alone does not identify which subsystem is wrong. Images, state traces and acceptance rules need to remain available together. Otherwise a reusable skill may preserve a workaround for a measurement mistake rather than a better way to manipulate the object.

Development records and frozen-version tests differ

The reported 91.1% average across eight physical tasks describes development attempts spanning program revisions. It should not be read as long-run reliability of one frozen version. The comparison of execution times addresses a different question: removing repeated online thinking can shorten task cycles, but the reported execution comparison excludes earlier exploration and development costs. Ethernet insertion remained without an agent-free solution after ten days. The paper also contains differing overall simulation figures, so this account does not promote a single headline score. Task, version and measurement stage are more useful distinctions than collapsing development progress into an implied production uptime number.

Reuse needs the conditions under which a skill worked

The repository separates environmental facts, attempted approaches and failure causes from executable implementations. That makes reuse inspectable, but an old skill still needs testing with the current objects and layout. Another observation concerns review overhead: an additional reviewer delayed new physical trials. Because the compared development phases occurred sequentially, the result does not establish that review is generally useless. A more grounded design lesson is to bound local repair loops and return stalled work for reconsideration of the method. Repeated, stable procedures may benefit from a tested program; unfamiliar contacts and changing environments can still require online diagnosis and human assistance.
