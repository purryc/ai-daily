When the first session stops at an occupied port

KiCad MCP Pro exposes schematic, board and manufacturing checks to AI clients, but establishing the connection is itself a failure-prone part of the workflow. Its desktop application needs a Python backend matching the application version. When a healthy older service already occupies the default port 3334, reusing it can be incompatible and terminating it can disrupt another working session. Version 4.9 adds a concrete choice: retain that service and launch the matching backend on port 3335. The user no longer has to decide which process is safe to kill merely to try the newer application, and a responding port is not automatically treated as a compatible backend.

The selected address must follow the user

The fallback is not an unlimited port search or an automatic cleanup policy. If port 3335 is occupied too, the attempt fails visibly. Supported local commands stay within the two defined ports, and both the dashboard URL and copyable diagnostic command follow the selected backend. This prevents a familiar partial repair: the new service starts, but the browser and troubleshooting instructions still point at the old one. Related work aligns project selection and readiness reporting across CLI, native IPC and DRC capabilities. Maintainer compilation and simulated IPC checks support the implementation, but they do not establish fresh signed-installer acceptance across all real desktop environments.

Review tools do not constitute manufacturing approval

The default tool surface is read-only review, with controlled writing and manufacturing release handled separately. It uses KiCad capabilities for ERC, DRC and exports and offers some first-order electrical, thermal and manufacturing estimates. Those are not substitutes for electromagnetic simulation, finite-element analysis or engineering sign-off. An AI client can gather findings, locate objects and explain a likely problem while a person remains responsible for the design intent and constraints. The repository dashboard shows components, nets and manufacturing status as a product example. A PASS label in that example is not evidence that a real production board was independently verified.

Local readiness and remote writing are separate

Cloud connection and account pairing also appear in the 4.9 work, but that does not make every remote write path generally available. The implementation record retains pending installed-environment acceptance, with fail-closed behavior around some Windows pairing and native remote writes. A user with an existing KiCad project first needs to know which service is connected, which project is selected and which operations are actually available. The port-recovery change makes those boundaries easier to follow. Existing KiCad commands or scripts remain straightforward for a fixed check; a shared readiness and recovery surface is more useful when the same project is inspected repeatedly through different AI clients.
