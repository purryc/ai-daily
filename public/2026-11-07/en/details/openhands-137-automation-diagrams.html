Explain the automation before asking someone to run it

An OpenHands automation detail page could previously open directly onto a prompt or script. A job created from the catalog could have no description of its own. Version 1.37 adds an explanation area that first uses saved Markdown, then the associated template, and otherwise generates a How it runs diagram from the trigger, event filter and prompt or entry point. A person taking over can identify what starts the job before deciding how deeply to inspect its code. This adds visibility to existing work rather than new execution authority. It can also expose an obviously misplaced filter or a task scope that differs from its name.

Invalid diagrams retain their source

Mermaid is integrated into the shared Markdown code component. It loads when a diagram is first needed, uses the interface theme, caches the rendered SVG and falls back to the original code block if parsing fails. Chat messages using the same syntax also benefit. Strict rendering mode is a component setting, not a guarantee that all agent-generated material is safe. The fallback is useful operationally: maintainers can still read the diagram definition and locate a syntax problem instead of seeing an empty panel. Teams should preserve that source and compare the visible sequence with the configured job when they review a change.

Catalog versions affect what appears

The author's before-and-after screenshots come from local checks of a GitHub review template and a custom automation. The PR explicitly says template-specific text and diagrams require an updated extension catalog. With the older pinned catalog lacking a diagram field, available text and the generated diagram provide the fallback. An image should therefore be described as an author-supplied development interface, not our hands-on result or proof that every user receives the full template immediately. During adoption, the frontend, extension catalog and template metadata need to be considered together. Otherwise a missing bespoke diagram may be mistaken for lost user configuration.

Use the picture to check real conditions

The release also fixes resumed-session placement in UTC history, titles during startup handoff, and empty-chat suggestions appearing before replay finishes. Together these changes can reduce uncertainty about whether work continued, but the release does not provide an independent completion-rate improvement. A focused check uses a custom job, compares the generated diagram with its event filters and entry point, and deliberately supplies invalid Mermaid to verify the fallback. Jobs with several conditions or external services may still lose detail in a compact picture. Permissions and final results must be checked against the actual configuration and artifacts; an attractive path through boxes is not a successful run.
