ProGram updates charts during computation and keeps linked views in step

Make computation available for interaction

Large-data exploration often makes people wait for a complete computation before discovering that they chose the wrong filter. ProGram lets a browser submit a query specification to a Python engine and receive partial results for rendering. Shared coordination can reduce bespoke scheduling work across views. For a reader, however, an early chart remains an incomplete answer. A practical interface should reveal what has been processed and whether the displayed relationship is stable. Otherwise responsiveness can encourage premature conclusions. The adoption question is whether users can revise an analysis intelligently while it runs, rather than simply whether the first visible chart arrives sooner.

Share progress and intermediate state across charts

Lockstepping lets related views advance over the same input chunks, while forking can reuse compatible intermediate state for a new query. Keeping clustering and projection aligned can prevent users from comparing views at different processing stages. Reusing accumulated statistics can also avoid unnecessary rereading. The interface still has to explain which views remain linked. If someone pauses a chart and later rejoins a synchronized group, the resulting progress change should be understandable. Shared computation is an implementation benefit; predictable interaction is a separate requirement. Test whether people can explain why a view changes, not merely whether the engine correctly schedules its queries.

Prioritizing queries does not prioritize individual records

Temporary priority can give a drill-down query attention before restoring its earlier scheduling level. The grammar prioritizes queries, not arbitrary records within them, and changes to filtering, transformation or binning may require a restart. Product copy should therefore avoid implying that every edit preserves all previous work. Compare the amount of discarded computation, time until a useful result returns and whether background queries continue making progress. If an application must inspect particular samples first, that requirement needs algorithm-level validation. A priority control in the interface does not by itself establish the ordering guarantees needed for that analytical task.

Separate expressive prototypes from available tooling

The authors demonstrate coverage by reproducing two systems and presenting eleven examples. The current engine supports CSV, and public code is promised after acceptance. Those facts support an interaction and architecture proposal rather than production readiness or proven user efficiency. Adoption would require checking data-source integration, cancellation, failure recovery and uncertainty presentation. A small comparison with an existing dashboard could ask users to explain the difference between an intermediate conclusion and the final result. Increased misinterpretation would count against the design even if it reduces backend code. A released installable version, license and independent performance evaluation remain unconfirmed.
