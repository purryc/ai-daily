Occasional touch and sustained editing impose different costs

The November 5 Tom’s Hardware review adds a useful distinction to the specification sheet: direct manipulation felt natural in some Blender work, but sustained reaching became tiring, and timeline editing did not clearly improve over keyboard and mouse. That is one reviewer’s experience, not a verdict on every application. It suggests testing occasional object selection separately from continuous precise editing. A team considering touch could give the same participant selection, zoom, fine-adjustment and undo tasks, then record unintended changes and returns to the trackpad. A feature that feels satisfying during a brief demonstration may still be a poor choice for a long production session.

Keep desktop density while adapting targets to input

Apple’s design session separates touch gestures, system gestures, hit targets, hover interactions and expanding controls. Those distinctions matter to a dense desktop application. Permanently enlarging every control can disrupt an established workspace, while translating taps into clicks can leave hover-only commands difficult to discover. A practical review should follow an entire operation: select an object, locate its available actions, adjust it, confirm the resulting value and recover from a mistake. The design question is how input and feedback fit together. It cannot be settled by adding a touchscreen toggle or by measuring how many controls respond to a finger.

Cancellation and multitouch state need explicit code paths

The engineering session illustrates moving from traditional mouse tracking to control events and gesture recognizers. Its examples distinguish direct touch and handle beginning, changing, ending and cancelling an interaction, alongside target expansion and gesture exclusivity. Product teams should therefore inspect interrupted drags, system gestures taking precedence and simultaneous adjustments, rather than accepting only a successful tap sequence. Specific dimensions in a code example should not become a universal design rule. Apple’s resource page lists Xcode 27.3 beta, documentation and online labs. This research did not compile the examples or test third-party compatibility; available development guidance does not prove that a particular application has completed the work.

Evaluate an upgrade through task outcomes

For a creator, an upgrade decision still belongs to the task: does touch remove cursor positioning, repeated tool switching or awkward viewpoint adjustment? These are observable questions that do not require an advance promise of overall efficiency. Keyboard shortcuts, a trackpad, a pen tablet and an iPad companion workflow remain alternatives worth comparing. The same person may prefer touch when reviewing a result and retain familiar tools while producing it. The review and developer material support examining that mixed workflow; they do not establish long-term adoption, assistive-technology compatibility or ecosystem-wide quality. An evaluation should preserve the ability to return to an effective existing input method.
