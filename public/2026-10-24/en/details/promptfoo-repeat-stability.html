Keep intermittent failures together

Two prompt versions can finish with similar average scores and still fail in different ways. One may consistently miss particular questions; another may alternate between correct and incorrect answers to the same question. Promptfoo 0.125.0 adds stability groups for repeated evaluations, matching the test, expanded variables, provider and prompt. Developers can repeat an existing evaluation and inspect passes, failures and errors within the same group instead of reconciling separate spreadsheet exports. The feature reuses the existing assertions. Repetition makes variation easier to find, but it does not add a business requirement that the test never checked.

Errors and cached answers retain their meaning

The CLI surfaces up to five groups containing both passes and failures, while JSON exports retain the complete set under repeatStability. Pass rates count scored rows and exclude execution errors. A high rate therefore needs to be read alongside the error count: an unfinished evaluation is not a correct answer. The implementation also remembers whether the target or grader reused cached responses. Groups with such reuse, or no scored rows, omit the Wilson 95 percent interval. That prevents repeated retrieval of the same cached answer from being presented as the evidence supplied by additional independent samples.

Resuming a run preserves its grouping

Repeat identifiers survive persistence and export, and retries or resumed evaluations retain the original repeat settings. Summaries use final comparison grades and preserve evidence of cached grading. This matters when evaluations run in continuous integration: retrying a failed provider call should not silently detach that result from its original group. The statistical interpretation still has conditions. Shared conversational history and changing external state can violate the assumption of independent runs with a fixed success probability. The maintainer verified these paths with local fixtures; those checks establish implementation behavior, not the stability of a particular model in a real customer workflow.

[S71]

Safe mode has a deliberately narrow scope

Another addition is safe mode, enabled through the CLI, environment or configuration. It blocks string-based JavaScript assertions and shared transforms within the current asynchronous evaluation, without changing overlapping or later runs. File callbacks and directly supplied functions remain supported. Executable providers, configuration modules, Python or Ruby assertions, and HTTP parsers are also outside this phase's coverage. A configuration downloaded from another person therefore does not become safe merely because the switch is enabled. The narrower use is a team that wants to prohibit inline expressions while continuing to maintain its own trusted extension files.

[S72]

Check the providers that the project actually uses

The release also makes the Claude Agent and Codex SDKs optional peer dependencies. Projects using those providers need to check that the corresponding dependency is installed instead of assuming that the main package includes every integration. Promptfoo is MIT licensed and can organize evaluations locally, but inputs sent to external providers still follow those providers' processing paths and usage charges. For a team already repeating model calls through scripts, the immediate saving is less custom code for grouping, cache annotations and reconciliation after a resumed run. Choosing useful assertions and explaining the failures remain the team's work.
