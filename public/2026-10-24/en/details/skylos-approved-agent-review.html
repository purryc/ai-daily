Identify the exact change being reviewed

A pull-request author can continue pushing commits after asking an AI reviewer for feedback. Without a version attached to the review, developers cannot easily tell whether a comment concerns old code or the change currently awaiting merge. Skylos 5.0 adds an agent-review command that starts with an approved review ID. Cloud approval identifies the repository, pull request, and exact base and head commits. The runner obtains its GitHub workflow identity and validates that the returned source bundle belongs to the current repository and review. The resulting findings have a specific version to discuss rather than an ambiguous moving branch.

Read source without executing the pull request

This entry point reviews changed source without installing or running the pull request's program. The implementation requires a particular GitHub workflow event, obtains an identity token, requests the approved bundle from Cloud and calls the model through that review's dedicated proxy. Its input is a collection of source texts with paths, rather than an arbitrary website or whole disk. Paths must be relative, unique and valid, with allowed source extensions. For repositories accepting outside contributions, this avoids executing contributor scripts merely to let a model inspect their code. It does not automatically resolve misleading text within that code or incorrect model advice.

Context limits are part of the operating conditions

The source defines concrete limits: no more than 30 files, 64 KiB per file and 512 KiB of source overall. Network responses are also bounded, and the returned findings are capped at 200. This suits a manageable change, not a promise to understand every dependency in a large repository at once. Oversized inputs fail rather than silently becoming a smaller review presented as complete. Splitting a pull request remains useful for the developer: a smaller change is more likely to fit the processing limits and gives human reviewers a clearer basis for deciding whether a model's finding actually concerns the proposed modification.

Findings must point into the supplied file

Each source file becomes analysis context, and the model must return findings in a prescribed structure. The runner checks the finish reason, required fields, rule identifier, severity and explanation, then verifies that line ranges lie inside the submitted file. Malformed output, incomplete generation or an out-of-range location fails the review. The error path attempts to record failure in Cloud instead of returning an empty list that could be mistaken for a clean result. Structural checks can remove unusable findings, but a valid line number does not prove a defect exists. The suggested change still needs semantic review and appropriate tests.

[S76]

Separate local scanning from the paid Cloud review

Skylos's existing static scanning can analyze code locally, while this new entry point explicitly uses a Cloud review proxy and is described in the command as a paid PR review. Apache licensing makes the public implementation available; it does not make hosted model requests free, and a verified price for this path was not established. Manual review, static checks and execution tests continue to serve different purposes. Static tools handle explicit rules, a model can explain suspicious logic, and people and tests check behavior. The update reduces manual alignment of approved commits, submitted source and model findings, without establishing an accuracy rate.
