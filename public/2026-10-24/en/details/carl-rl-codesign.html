Turn domain knowledge into a specification

A reinforcement-learning project can begin with a goal that sounds clear while leaving crucial choices unstated: what the policy can observe, which actions are admissible, and how failure affects reward. CARL puts those choices into a ten-step conversation before implementation. Its Trillian assistant proposes domain-aware answers, which the expert can accept, edit or reject. The intended participant knows the problem but may not be an RL specialist. This changes the handoff: the person helps construct an explicit specification before a coding loop turns it into a training pipeline. It does not make domain judgment disappear. If the human approves the wrong objective, technically successful training can still solve the wrong problem.

Carry decisions between steps

Each stage has its own skill file, and compact summaries preserve the decisions carried into later stages. The implementation provides both web and terminal interfaces, with session artifacts rather than a disposable answer as the output. For a practitioner, that makes the handoff inspectable: a changed reward can be connected to a new run instead of disappearing inside a rewritten prompt. The same choice also creates a review obligation. A short summary is useful only if it keeps the constraint that mattered. When a later result looks wrong, returning to the recorded decision is more informative than asking for another plausible explanation of the plot. This is structured assistance for problem formulation, not just a chat skin over code generation.

Diagnose the policy before another run

The paper demonstrates goals-based wealth management and a dynamic-pressure-constrained Goddard rocket problem. These are author experiments, not financial advice or operational flight deployments. Their relevance is the distinction between a bad implementation and a bad specification. An expert reviewing a learned policy may discover that the reward encourages an unwanted shortcut or that the state leaves two different situations indistinguishable. Another run with the same formulation will not necessarily repair either issue. CARL offers a place to revisit the formulation after seeing results. The approach is most compelling when those decisions are still being explored; a fixed rule or an available analytical solution may be easier to maintain for a settled task.

Self-hosting still needs model access

The public repository supplies GPL-3.0 code, including the controller, workflow skills, session handling and report components. It can run on a local workstation without SageMaker, but its current language-model integration uses Amazon Bedrock Converse. AWS credentials and model access remain necessary; a completely AWS-free local provider is not included. Python 3.10 or later is recommended, and training compute and model usage remain operating costs. The repository also deliberately omits previous sessions, screenshots, logs and historical runs. That makes it a usable starting implementation rather than a complete archive of every reported experiment. Teams should check their available model access and execution environment before budgeting time around the conversational interface.
