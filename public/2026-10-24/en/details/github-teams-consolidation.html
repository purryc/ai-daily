Start a fix from its notification

A bug notification arrives in a Teams channel, followed by reproduction steps, the affected page and the expected behavior. Someone previously had to assemble that discussion again in a coding assistant or issue. The consolidated GitHub application lets a member mention @GitHub beneath the notification and request an investigation, code change or test. The linked issue or pull request and the conversation become the input to work in a cloud sandbox. The result is a proposed pull request returned to the team. People still review, test and merge it; a chat instruction does not replace the repository's review process.

Continue the same task with later messages

The response identifies the repository, model, status and resulting artifact. Mentioning @GitHub again in the same thread incorporates messages added since the previous invocation, while work can also continue in GitHub, a terminal or an IDE. Channels support a default repository, and the first session can establish one when none exists. Direct messages do not have that channel default. Omitting a branch uses the repository's default branch. Explicit repository and branch arguments therefore remain useful when a conversation spans several codebases: an accurate request is still unhelpful if it is assigned to the wrong location.

Thread context and execution identity belong together

The input scope is the entire thread, not only the sentence containing the mention. Documentation says that context is retained with generated artifacts, so starting a separate thread or direct message can keep unrelated material out. Direct messages use the connected person's permissions; shared conversations use application identity. Repository write permission is required to trigger changes, and guests or outside collaborators cannot start or steer work, although other participants can contribute context. Additional approval applies to app-created pull requests under repository rules requiring approval. That condition should not be presented as an identical rule imposed on every repository.

The change also involves an application migration

The October 23 announcement concerns the combined application, not Copilot's first appearance in Teams: related improvements were already announced on October 15. Teams using the notification application can update it and add agent access. A separate legacy GitHub application has been renamed GitHub (deprecated) and is scheduled to retire on November 16. Administrators need to identify which application is installed rather than relying on a familiar name. Current integration documentation still labels the capability public preview. The announcement has a calendar date without an exact clock; this issue treats it as a recent supplement rather than inferring an in-window release time.

Less repackaging, with repository work still visible

Receiving notifications does not require a Copilot subscription. Calling the agent requires eligible paid access, an enabled cloud environment and, where applicable, organizational permission. The integration is most useful when a team has already explained a problem in Teams: it removes another round of copying reproduction steps and reconstructing context. It cannot supply a missing repository or turn an unresolved discussion into a precise requirement automatically. Starting an agent task directly in GitHub remains an alternative. The public material does not quantify time saved, and recovery after failed multi-turn changes was not tested here. Subscription eligibility and the quality of the resulting pull request are separate questions.
