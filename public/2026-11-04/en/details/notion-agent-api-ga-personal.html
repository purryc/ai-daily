Give an existing agent another front end

The November 2 changelog confirms general availability and access to the personal assistant through the notion_ai identifier. A team can expose an existing Notion agent through an internal application or mobile front end while retaining its configured behavior. The quickstart explicitly says Custom Agents must already exist in Notion; the API does not create them. This helps relocate an established workflow to the tool someone already has open. It does not produce the new application's interface, review experience or error explanations. The developer still decides which messages belong to one conversation and where the person takes over when the next action requires judgment.

Token choice determines conversation continuity

A personal token acts with its owner's access. A connection token reaches Custom Agents explicitly shared with that connection and cannot use the personal agent. Ownership then affects continuity: a personal-token conversation can continue in the Notion app, while a connection-created session has no associated user and must continue through the API. Authentication is also a handoff decision. If an external interface starts a task that a person will review and extend inside Notion, personal-session continuity is relevant. If the service owns the conversation, it needs its own continuation surface instead of implying that the chat automatically becomes a team member's personal conversation.

Resume from committed events after interruption

The migration guide replaces threads and messages with sessions and events, distinguishing provisional output from committed records. Reconnection uses the last committed event ID; a sequence number, temporary fragment or stream-control record is not that recovery point. The API also exposes queued, running and action-required states. The client should represent those differences visibly. Text already shown on screen may not yet be durable, and waiting for a person's choice is not the same as failure. Keeping only final prose can lose the state needed to finish a multi-step task. We have not tested interrupted connections or duplicate delivery, so these are documented mechanisms rather than measured reliability.

Usage is visible, but management rights differ

The insights endpoint reports credits and run counts for a specified window. Personal-agent totals belong to the token's user, rather than providing access to another member's consumption. The personal assistant supports name and model changes but lacks the Custom Agent status and per-agent limit controls. The quickstart places Custom Agents on Business and Enterprise plans and notes that personal-token creation can be restricted there by default. Adoption needs clear session ownership, configuration authority and usage visibility together. General availability describes the API's release stage, not zero-cost execution. The examined documentation establishes no universal fixed price per task, and no billing sample was generated for this report.
