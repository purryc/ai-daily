OpenHands shows the submitted task while startup continues inside chat

See what was submitted before startup finishes

Cloud conversation creation previously kept users on Home until the creation response arrived, making it easy to doubt whether submission worked. The new flow first shows a client-side conversation view with the submitted prompt and file names, then updates startup progress inside chat. Edit and retry remain visible on failure, and pending starts remain reachable from the sidebar. This changes the feedback sequence rather than guaranteeing faster server startup. Showing the actual request may reduce the temptation to submit twice. The interface must still distinguish local presentation from server acceptance; a visible message bubble is not itself proof of receipt.

Put activity beside the work being read

A running stage is grouped from its first step, with a header identifying the current action. Between steps it shows thinking; after the agent's next message it becomes a settled summary. The old activity chip above the composer disappears, reducing the distance between the work and its status. Starting as a group also avoids restructuring a single row when another action arrives. The author added a screen-reader status region but explicitly did not test VoiceOver or NVDA speech. The placement supports continuity, while browser semantics alone are insufficient to claim complete accessibility validation across assistive technologies and real usage conditions.

[S89]

Repository selection and conversation organization have different scopes

Cloud repository selection is remembered per backend, shown on return and checked for a usable provider and branch. Invalid selections are discarded, and a clear control is available. Conversation pins and archives separately move from browser-local state into server-side tags, so they are no longer limited to the browser that created them. Both reduce context-recovery work, but their storage scopes differ. Remembering a launch repository is neither permanent authorization nor an instruction to retarget every conversation. After an upgrade, a developer should still inspect the selected project before submitting work rather than assuming that a convenient default necessarily matches the new task.

Read what the author's comparison actually measured

The startup PR reports three matched warm runs per version. Median prompt visibility moved from 1,056 to 84 milliseconds, while the first actual agent reply was about 5.922 versus 5.919 seconds. The author also says route commitment still takes roughly a second, so faster visual feedback should not be reported as an end-to-end speedup. These are developer measurements from a small sample, not independently reproduced results. Version 1.35.0 packages the changes in the November 3 release. Earlier coverage of 1.33.0 concerned machine defaults and automation status, a different increment. An upgrade evaluation should check client, backend and model configuration, especially failure recovery and existing conversation state.
