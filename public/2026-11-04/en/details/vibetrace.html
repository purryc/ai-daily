Locate the first wrong step

Long coding sessions create a navigation problem: finding the first mistaken step among many otherwise reasonable actions. VibeTrace organizes OpenCode activity into tasks, subtasks and linked actions. Developers can inspect a step and branch with a correction. The value should be measured through diagnosis: can someone tell whether the agent read the wrong file, misunderstood a requirement or omitted verification? A diagram does not itself establish causality. Links back to actual inputs and outputs matter because a persuasive visual story could otherwise hide gaps in the record. The useful comparison is time to a defensible intervention, not simply preference for a more attractive display.

A branch preserves comparison, not every external state

The repository describes branching into a new OpenCode session while retaining a snapshot and visual comparison. That provides a concrete place to attach a correction. For deployment, however, we would separately examine conversation context and environmental state. A new branch should not be assumed to reverse files, running processes or external service actions. A useful pilot starts with repeatable local tasks and an explicit code snapshot. Compare the resulting changes and identify which state was reused. This distinction matters because the visual metaphor of returning to an earlier point can imply stronger rollback guarantees than the underlying system provides. Recovery should be demonstrated, not inferred from the diagram.

The benchmark uses twenty held-out tasks

The skill experiment uses thirty distillation tasks and twenty held-out tasks, repeated five times with a shared model and verifier-simulated feedback. It reports a pass-rate change from 65% to 68%. A separate twenty-person study compares understanding of ten recorded traces with native logs. These address different questions: transfer of procedural guidance and comprehension of execution records. Neither alone establishes improvement across an entire development project. A follow-up should use unfamiliar repositories and naturally occurring corrections, then examine whether guidance helps on new failures or merely matches recurring benchmark structure. Include unsuccessful interventions and the time spent deciding what to preserve.

Reusable guidance needs a way back

Experience is stored as skills rather than trained into model weights. The public repository specifies an MIT license, OpenCode, Node.js 20 or later and Python 3.9 or later; model access remains a dependency. We would initially limit new guidance to a small project scope and retain its source trace and previous version. The important failure case is a one-off workaround becoming a default rule. For example, an emergency exception should not quietly spread to unrelated tasks. Review should cover both whether the new skill helped and whether deleting it reliably restores prior behavior. The code is inspectable, but this issue does not report installation or independent runtime testing.
