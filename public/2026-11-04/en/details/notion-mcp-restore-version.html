Find the state before the mistake

A shared proposal can contain human edits, AI rewrites and actions from connected tools. Notion MCP already lets an assistant find pages, change content and manage databases. The November 3 addition puts historical restoration into that workflow. A useful request therefore identifies both the affected item and the desired earlier state. The recovery goal needs more precision than a phrase such as “go back to Monday.” Later work may include a corrected budget or newly assigned owner that should survive. The practical benefit depends on connecting the reported mistake to a recoverable state without treating all subsequent collaboration as disposable.

Preview comes before the write

The reference specifies a two-step call: omit user_confirmed first to obtain a non-mutating impact preview; show that result to the person, and send user_confirmed: true only after agreement. Execution then proceeds in the background. This matters because a vague instruction becomes a reviewable proposed write. A useful approval surface should make the target, time and scope understandable rather than merely asking whether to continue. Background execution also creates a handoff between an accepted request and a completed repair. We did not call the tool, so the documentation does not establish a tested completion display, retry behavior or protection against simultaneous edits.

[S62]

Recovery does not traverse every child

Restoration reverses later edits and removes later comments, while child pages and database-row bodies keep their content. Inline databases require an explicit include_inline_databases choice. A project homepage and the detailed plans inside its task rows can therefore have different recovery boundaries. A page that looks repaired is not proof that its linked work has also returned to the intended state. The ordinary Notion help guide offers another route: copy selected blocks from an older version into the current page. This narrower repair can preserve valuable later contributions when the damage is local, whereas a full rollback is easier to reason about for a clearly bounded incident.

History depth still belongs to the workspace plan

The tool requires edit access and update-content capability; connecting an assistant does not extend retained history. Notion lists seven days for Free, thirty for Plus, ninety for Business and longer history for Enterprise. Its help page also describes periodic version capture, rather than a snapshot of every keystroke. The update therefore changes access to existing recovery data; it cannot promise every intermediate state. Reviewing changes and authors can help a team select the right point. Recovering a deleted page is a separate Trash operation. Keeping historical rollback, deleted-item recovery and backup retention conceptually distinct makes it easier to choose the repair that actually matches the incident.
