Avoid retransmitting the same history

Ordinary Messages applications assemble the conversation history that the model should receive. A thread changes transport and reconstruction: the first request provides the conversation, while later requests identify the previous response and carry the newly added messages. This can suit consecutive user replies or tool results. Frequent turns are the most relevant evaluation case because their request bodies would otherwise keep growing. A chat used only occasionally may behave differently when server state has expired between replies. The change does not create unlimited model memory or decide which information belongs in the task; those remain application design choices.

Expiry and deletion are different deadlines

The release notes distinguish expiry from deletion: a thread expires five minutes after its last request and is deleted no later than one hour after its last use. A developer should not treat that interval as a conversation database. The application must retain its own record and recreate the thread when continuation is unavailable. Normal operation and recovery should draw from the same authoritative history. Otherwise a background task can continue one branch while the interface presents another. The vendor describes improved time to first token, but no request benchmark was performed here, so there is no independently established speedup or guaranteed latency reduction.

Smaller requests do not automatically enable caching

Prompt caching has its own control surface, using cache_control at the request or content-block level. Automatic caching moves a breakpoint with the growing conversation; explicit breakpoints give the application more direct placement control. Threads can be combined with caching, but a smaller network request is not proof that all input became a cache hit. A useful evaluation separates bytes uploaded, time to first token and usage records. Those measurements describe different bottlenecks. In document question answering, retrieval and tool execution can also dominate the wait that a user experiences. Attributing the whole task duration to repeated message transport would therefore overstate what this feature changes.

[S95]

The SDK helper is not durable storage

The SDK helper keeps conversation history in its own memory and assists with creation, continuation and replay. Persisting beyond the application process still requires application storage. Instructions and tools belong to creation, and changing fixed fields requires a new thread, making this an append-oriented interaction rather than arbitrary editing of sent history. Availability covers Claude API, Claude Platform on AWS, Anthropic-managed Google Cloud and Microsoft Foundry. The documentation marks the feature as ineligible for ZDR and HIPAA. These are material adoption conditions: evaluate the short server retention, the application's own storage and the chosen cloud entry point together instead of treating the beta header as the entire integration.
