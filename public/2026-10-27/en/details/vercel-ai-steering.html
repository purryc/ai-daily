Correcting a running task

A person using a weather lookup, research assistant or multi-tool workflow may notice a missing condition only after execution starts. An application could previously drain its own queue before each step, but a message arriving during the final answer might never reach another step. Saving the result could also omit that correction from history. AI SDK 7.0.154 adds an explicit handoff: the application creates a steering object before starting generation or a ToolLoopAgent, then submits later user messages through it. The input is still an ordinary instruction. The additional output is a delivery result that the surrounding interface can use.

[S77]

Delivery happens between steps

Delivery occurs after the current step and its tool calls finish. Each correction becomes a separate user message in arrival order. A pending correction can extend a loop that would otherwise finish its answer, but existing stop conditions still take priority. Calls configured to stop after one step therefore need suitable loop settings. This creates a visible interval between pressing Send and the model receiving the correction. A product can show that it will be handled at the next step, rather than suggesting the ongoing action has changed immediately. An email already sent or a completed write is not undone by this mechanism. Each steering object belongs to one invocation. Starting a fresh task requires a fresh object, so the application needs to keep task identity attached to its message queue.

A result the interface can explain

The documented outcome separates delivered and undelivered messages and preserves the message identifier and reason. A finished run, stop condition, pending tool results, abort or error can prevent delivery. A preparation function that rebuilds history and drops the correction has its own failure reason. Submitting the same identifier again returns the first outcome, helping applications handle network retries without appending a duplicate instruction. Delivery means the message entered the model input; it does not establish that the model followed it. The finished artifact or action result remains the evidence that the city, scope or requested format actually changed.

[S77]

Persistence remains application work

Steered messages are not automatically included in responseMessages. Applications need to save each step’s steering messages alongside assistant responses in order, or a reload may show a change of direction without the instruction that caused it. The maintainer identifies streamed UI chunks, steering across processes and broader agent support as follow-up work. This experimental API therefore suits teams that already own an agent loop and its interface. Useful checks include sending a correction during the final answer, during an approval wait and before reloading saved history. A successful message during an ordinary tool call covers only one of those situations.
