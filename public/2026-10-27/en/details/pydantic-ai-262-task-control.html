Keep communicating after delegation

After an application delegates research, the user may add another condition. If the application can only wait for the finished answer, that condition needs a separate queue or a restarted job. The optional TaskControl in SubAgents gives the delegation an ongoing identity: a background request returns a receipt, the parent continues other work, and later messages or answers can reach the child. The result arrives as a message before the run ends. Inputs therefore include revisions and answers received during the task, while outputs include states and events as well as final text. This fits products already waiting on long tool runs or external material. It is less compelling for a short request that can be handled without introducing another agent.

Route questions and corrections to the right task

The implementation describes tools for listing tasks, sending messages, answering and cancelling, with children able to ask the parent questions. Routing has an explicit family boundary: the parent messages, answers and resumes its child, while an ancestor may cancel it. That reduces accidental cross-talk, but the application still needs to show which task will receive an answer. “Change this to the European market” can mean different things in two parallel investigations. Cancellation also distinguishes a stop request from forced cancellation. An interface should know whether it has requested termination or observed a completed transition. If a tool has already changed a file, sent a message or placed an order, ending the model run does not undo that external action; recovery belongs in the business tool contract.

Events supply the interface, not a finished dashboard

Task state remains in DelegationTasks records, with typed events available on the delegating run and the owner’s observer. An application can use these to separate waiting for an answer from active execution and to connect policy checks to consequential transitions. The saving is a reusable communication mechanism, not a finished task dashboard. Task names, concurrency limits, error summaries and whether the user sees a current status remain product choices. Without an externally bound owner, the run manages its own task lifetime; background does not mean indefinite work after exit. An acceptance timeout handles a remote task nobody picks up, but worker heartbeats are deferred. That leaves a meaningful gap between task controls and a scheduler that can diagnose every lost worker.

Existing history readers need an upgrade check

The same release also records thinking-effort changes in message history and lets supported adapters send an in-conversation settings update, reducing cache disruption from changing request settings. This is not uniform across every model or step. The linked PR says Anthropic waits for a subsequent user turn with new input when the current step contains only tool results. Applications that exhaustively handle message or event types must recognize the new settings-delta records instead of upgrading the dependency while retaining old serialization assumptions. Task control itself remains opt-in and explicitly unsupported under durable execution. For an existing product, one realistic sequence containing a question, correction and cancellation offers a clearer migration check than enabling every parallel option at once.
