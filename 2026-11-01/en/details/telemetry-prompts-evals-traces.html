Find the failed step within a run

When an agent fails, its final answer seldom reveals whether the model misunderstood the request, retrieval missed a document or a tool timed out. telemetry.dev represents a run as a trace and its model and tool calls as spans carrying duration, tokens, cost and errors. Developers connect TypeScript or Python instrumentation, or an existing OpenTelemetry exporter, then move from an unusual run to the relevant step. The October 31 maker launch specifically names prompt management, evaluations, alerts, CLI access and MCP access as additions. That dates the launch discovery rather than the invention of every tracing feature. A located error narrows the investigation; somebody must still interpret the returned evidence.

Keep the prompt version attached

Prompts live in the service while application code fetches a version through a label such as production and fills its variables. The model span records the prompt name, version and label. A developer can send a fraction of calls to a new version, compare errors, latency and cost, and move the label back if the change performs poorly. This removes a deployment from routine wording changes and preserves which text produced a particular answer. Test runs use the developer’s own model key. The application must still adopt the retrieval integration; pasting a prompt into an editor alone changes nothing in production. The illustrated refund response is demonstration data, not evidence of successful real refunds.

Keep the execution path during evaluation

Evaluation can preserve more than a pass score. AI SDK and TanStack AI evaluation calls appear as Evaluate spans with underlying model and tool activity, allowing the same cases to be compared by spending and failure location. The project’s Evals area handles datasets, experiments and scoring, while a separate environment keeps test traffic out of production metrics. A failed case can therefore be traced to an order lookup or policy retrieval instead of prompting a blind model change. Developers must configure that separation, and evaluation spans consume ingestion units. Whether the dataset represents real users and whether a score catches the important error remain evaluation design decisions rather than automatic properties of the dashboard.

MCP correlation needs client context

The MCP transport wrapper records client and server activity and distinguishes tool errors, transport failures and invalid requests. A separate read-only MCP interface lets a coding agent search traces and inspect span trees. Arguments and results stay out of spans by default, although method names, resource addresses and error details remain. In the launch discussion, the maker explains that a remote server cannot reliably group calls when Claude’s web or desktop client supplies no conversation or trace identifier. Returning a session identifier for the model to repeat is only a memory-dependent workaround. A complete run trace therefore depends on correlation data; a collection of server calls cannot automatically establish the entire agent conversation.
