Request work inside the existing discussion

The prototype works within one GitHub repository. A team requests work in GitHub, or in Feishu when that optional source is connected. The system checks who asked and whether the request fits the allowed scope before creating a work item. That item receives its own agent session and directory; results, such as a pull request, return to the original conversation. Users therefore do not have to open a separate chat just to transport the request and its outcome. The README stresses that the published code differs from the internal implementation and does not implement every direction discussed in the design article. Broad promises of autonomous collaboration must be checked against the actual published workflow.

Give each piece of work a durable identity

The domain documentation keeps events, threads, acceptance decisions, tickets and execution distinct. Events enter their source threads; subscribed tickets receive additional context, while other events pass through evaluation for new work. An accepted ticket carries a mandate before an executor takes it, and reports use the originating channel. Accepting the same event again creates only one ticket, while sources retain a read position so a restart need not replay old events as new requests. For maintainers, this addresses a concrete coordination question: which piece of work does this reply belong to? It cannot review a patch for them, but it gives retries, clarification and reporting a common identity instead of relying on remembered chat windows.

Context does not automatically become permission

The authorization document separates message content from permitted action. The host enforces allowed lists, rules and ticket mandates; comments, quoted documents and other incoming material are decision inputs rather than permission changes. An allowed person explicitly addressing the agent can request work, whereas an admitted bot event can only become a candidate for evaluation. Subscribed threads continue delivering context, including CI and bot messages, without granting additional authority. In a shared repository, someone attaching a log therefore does not authorize edits across every module. Operators still have to write understandable policies and check that the ticket reflects the request. These are documented implementation constraints, not a certification that every misleading input has been defeated.

[S112]

Put human attention on outstanding decisions

The Superagent web sidebar orders information around work needing a person, system health and the history of an individual task. Overview surfaces outstanding tickets and problems. Execution distinguishes waiting, working and ended states, while ticket details connect the originating event, decision reason, authorization and subsequent input. Failed input delivery or reporting can be retried; ended items show outcomes such as a merged pull request or a human stop. Missing repository or account setup is surfaced explicitly. This reduces the need to inspect each conversation for stalled work, provided deployment and integration are correct. The MIT-licensed project asks operators to review and adapt the code, warns about defects, and has no independent long-running team evaluation in this report.
