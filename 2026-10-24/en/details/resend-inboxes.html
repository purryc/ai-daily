Receiving mail is only the beginning

Connecting a support address to an application still leaves a developer with repeated replies, ownership, draft status and message classification to manage. Resend already offered receiving webhooks. Inboxes adds an own-domain mailbox, conversation threads and queryable handling state around them. Incoming messages become part of a conversation that teammates can assign and annotate, while an application can read the thread and reply through an API. This removes some repeated work for teams building support or recruitment tools. It does not decide the underlying business policy, such as whether a refund should be granted or a candidate should proceed.

People and agents work on the same mail objects

The mailbox exposes folders, labels and queries such as sender or date. A team does not need to copy every message into a separate chat transcript before an agent can work on it. Resend describes API, MCP, CLI and skill-based connections, alongside instructions, tone and permitted actions for its built-in agent. Allowing a draft or label is a different choice from allowing forwarding, archiving or deletion. The presence of drafts therefore does not mean that every automatic action requires human approval. A useful configuration follows the job: categorize incoming requests first, then leave a consequential business decision with its owner.

Retrying draft creation does not rewrite a draft

The draft API distinguishes a new conversation from a reply. A reply supplies both the thread and the message being answered. Only one unsent reply draft can exist for each email. Repeating the creation request returns the existing draft ID and changes attachments, rather than silently replacing its body with the new request text. Editing the body requires the update operation. That matters when a person has already corrected an agent's draft: a network retry should not be mistaken for permission to overwrite it. Idempotency and conflict responses also require explicit handling; a successful response does not necessarily represent another newly created draft.

[S52]

Domain setup remains an explicit prerequisite

Creating an inbox requires more than submitting a name. The normal receiving path requires receiving to be enabled, verified DKIM and SPF, and the documented MX status. Forwarding mode has different requirements and supplies a receiving address to which an existing mailbox can forward messages. An existing address produces a conflict, while exceeding the plan's inbox allowance produces a separate error. Keeping an established mail entry point and forwarding from it is different from making the new inbox receive directly. The team must still account for its actual domain and mail routing; a short API request does not remove that setup.

[S51]

The offer fits custom workflows, with costs beyond mailbox count

The product page lists three free inboxes and 3,000 sent or received messages per month. The announcement lists additional inboxes at one dollar each, but the billing period and full model-usage cost were not established here. The offer fits teams already connecting email to their own product and seeking fewer thread and assignment components to maintain. It is not automatically a replacement for every established support suite: order lookup, customer identity and business rules still need connections. October 22 is the detailed announcement date used here. Earlier launch leads remain unresolved, so this is a recent supplement, not a claim of first availability today.
