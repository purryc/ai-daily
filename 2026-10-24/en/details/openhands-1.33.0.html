OpenHands keeps web cloud accounts connected and makes the machine choice explicit

A restart need not mean pasting the cloud token again

The web version of Agent Canvas previously kept DigitalOcean credentials only in server memory, requiring another token paste after a restart. Version 1.33.0 fills that gap for the optional web bridge. After connecting, the user sees the team or email identity and where the credential is saved; the connection can be found again after restarting. This concerns account state on the machine hosting Canvas, rather than storing the token in the browser. Desktop Canvas already used its Electron storage mechanism, so the change is neither first-time persistence across every platform nor automatic enablement of cloud access for every installation.

The interface identifies where credentials are saved

The implementation prefers the host's system secret store: Keychain on macOS or Secret Service on Linux. An encrypted-file path uses OH_SECRET_KEY. When neither persistent option is available, the application retains credentials in memory and displays a not-saved warning, rather than leaving discovery until the next restart. The connection-list file itself contains no token. Browser admission cookies are separate from cloud credentials, and changing the Canvas session key invalidates old cookies. Maintainers documented live Linux checks, while the actual macOS Keychain path lacked equivalent live testing. Unit coverage should not become a claim that every platform was exercised.

[S54]

Choose a concrete machine size before creation

The new DigitalOcean agent form sorts available sizes by virtual CPU count and then memory, selecting the smallest entry instead of leaving the choice to the provider. Larger machines and an explicit provider-default option remain available. A delayed, failed or empty catalogue cannot silently submit an unspecified size, and a late catalogue response does not overwrite an existing choice. This removes ambiguity about what will be requested. It does not demonstrate that the smallest machine can run every workload. The maintainer's recorded check stopped before creating a machine, so it supplies no measured cloud-cost saving or inference result.

[S55]

A visible phase is separate from successful completion

Automation runs already had an overall status, but the interface expected phase fields that the backend did not provide. The update reads the actual current_phase value and displays it in automation cards, activity records and pinned home cards without a reload. Failed runs retain their last phase; completed runs hide it; older backends without the field do not acquire invented progress. The maintainer's demonstrated run ultimately failed because model authentication was missing. Its screenshot can establish that a phase appeared, not that the agent completed the job. This gives users more specific information about where work stopped than a generic status alone.

[S56]

Less exposure while entering secrets, with runtime costs separate

Secret-request cards and the add/edit forms in Settings now share a masked password field. An eye control reveals only the current entry, and switching secrets resets visibility. That addresses plain text appearing during screen sharing; it does not alter the API or backend storage contract. Release packages cover Windows, Linux and Mac, with Mac signing and notarization still incomplete. The repository uses MIT licensing, while model services and DigitalOcean machines carry separate costs. For existing Canvas users, these changes reduce repeated sign-ins, ambiguous machine choices and opaque progress. They do not demonstrate an improvement in the model's coding quality.
