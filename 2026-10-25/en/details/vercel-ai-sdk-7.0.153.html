Vercel AI SDK 7.0.153 · Developer-tool update

Vercel AI SDK parses the last final JSON without discarding earlier content

Two valid objects do not become valid JSON when concatenated

A Responses reply can contain a JSON draft followed by a revised final answer. Each object may be valid independently, yet concatenating them produces invalid JSON. In a form-filling, list-extraction or report-generation application, the model appears to have answered while the product still requests another attempt. Version 7.0.153 allows a provider to supply a separate text value for structured parsing. OpenAI and Azure Responses adapters can select the last message marked final_answer. The fix concerns response organization, so users need not repeatedly strengthen a prompt to demand only one JSON object when the provider has already identified which message is final.

Keep the business object and the full response separately

After selecting the final answer, generateText exposes its parsed result.output and generateObject provides the corresponding object. Full text, content, response messages, annotations and usage remain available separately. Developers can therefore retain both validated fields and the complete response without deleting earlier material merely to make parsing work. Full text may still contain several JSON objects. An application that bypasses the SDK object and manually parses text can reproduce the original concatenation problem. Adopting the patch includes checking which field actually drives the interface or downstream action, rather than assuming a version upgrade changes every custom parser in the surrounding application.

Middleware must also transform the selected parser input

Some applications remove Markdown fences or extract JSON from model text before schema validation. Built-in JSON and reasoning middleware now also processes the separately selected structured-output text, avoiding a mismatch where the displayed response is cleaned but the parser input retains its wrapper. The implementation keeps complete text and metadata available to callbacks. Business logic needs the intended final object, while investigation needs the other material the model produced. Separating those needs reduces custom string slicing. External middleware still has to understand and preserve the provider’s selected field; a wrapper that discards unknown response fields can defeat the intended behavior even when the underlying model adapter is current.

[S84]

The patch changes parser selection, not factual accuracy

The maintainer reproduced the issue with a simulated Responses payload containing commentary and final_answer messages, adding regression coverage for object generation, text generation and middleware. That establishes a specific input shape addressed by the change, not cross-model accuracy or an editorial runtime result. Streaming was not changed, so a product using streamText cannot simply adopt the same conclusion. A successfully parsed final object can still contain incorrect values or violate business rules beyond its schema. The patch is useful for teams encountering valid final answers broken by concatenation; it supplies no evidence that unrelated requests become faster or that extracted information becomes more accurate. Format validation and business correctness remain separate responsibilities in the surrounding application.
