Separate changing code from proving the change

Trail of Bits presents patching-bugs and regression-hunt as complementary workflows for repair and checking. Their code entered the public repository on October 20, before the October 21 announcement, so this is a three-day supplement rather than newly available code today. A conventional handoff gives an agent a defect description, reads its repair summary and leaves engineers to reconstruct validation. These plugins separate reproduction, independent confirmation, implementation, proof and regression checking into roles with retained files. The maintainer can inspect which revision and run support a conclusion. The deliverable is a prepared patch and review evidence, not an automatically completed production release.

Inputs include a running system and project constraints

Patching-bugs requires a clean local Git checkout, a working project build and a run directory outside the tracked tree. Its coordinator handles one supplied defect or falsifiable hypothesis and does not push or open a pull request. Regression-hunt accepts selected PRs, commits or ranges while the host supplies execution tools, authentication and resource limits. Project threat models and patching guidelines define behavior that must remain supported. Helper scripts require Python 3.13 or later, but validating records does not establish that their contents are true. A repository without a reproducible deployment still needs that groundwork; installing the plugin cannot remove the adoption cost.

A complete revert strengthens the causal check

The patching workflow runs one reproduction against original code, patched code and a complete revert: failure, success and renewed failure strengthen the claim that the patch caused the improvement. Regression-hunt traces a change to a reachable interface, reproduces behavior on before-and-after deployments and asks fresh contexts to replay and adjudicate it. Results distinguish confirmed regressions, older defects, incomplete repairs and unresolved cases. Missing proof is not evidence of absence. Independence here means fresh contexts and retained material available for checking, not a guarantee that model errors are statistically independent. Maintainers still need to examine the actual deployment, inputs and logs behind the report.

Fewer false alarms do not mean more defects found

Using twenty-one confirmed regressions, the authors report twenty-five percent fewer false-positive findings than a generic Codex regression-review prompt, with a fourteen-to-thirty-eight-percent confidence interval. Stricter proof requirements also left some known regressions borderline. This preliminary author evaluation is not a universal twenty-five-percent accuracy gain. For maintainers, fewer false alarms may reduce review work while unresolved cases still require investigation. Their absence from confirmed totals does not remove the underlying risk. An adoption evaluation should therefore track confirmed real defects, false alarms and unresolved cases together, retaining the denominator and selection method for each instead of choosing only the most favorable metric.

Recovery records determine the human handoff

The documented resume path checks artifact hashes and saved agent state; changed source or reproductions require new downstream attempts. That is a workflow contract, not a successful run independently demonstrated here. Manual peer review, existing CI and individually maintained reproductions remain alternatives. A harmless defect set can compare total review time, replay success and the effort needed to resolve inconclusive cases, including whether an engineer can reach raw evidence from the HTML report. The repository uses CC BY-SA 4.0, which should not be mislabeled MIT. If engineers still reconstruct every experiment, a longer report changes presentation without removing handoff work. The useful outcome is evidence that another person can efficiently inspect and repeat.
