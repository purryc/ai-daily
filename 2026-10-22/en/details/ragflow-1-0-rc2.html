A candidate release, not a new platform

RAGFlow 1.0.0-rc2 was released at 09:49:48 UTC on October 16 and is included as a seven-day lookback. It targets developers and knowledge teams turning complex documents into queryable material. The release exposes Agentic chat, adds Team/Me sharing and unifies built-in and Pipeline parsing choices. The earlier rc1 Go rewrite should not be counted again, and rc2 remains a release candidate. Maintainers state that rc1 data is compatible with a direct upgrade. That is a migration claim to verify on a copy, rather than a reason to omit backups, inspectable migration results or comparison of answer quality before and after the change.

A parser choice must match the configuration

The parser change replaces separate radio controls and conditional fields with one selector, while keeping built-in and pipeline identifiers distinct. Dataset creation requires an explicit parser type; updating unrelated configuration should retain the existing selection. The practical workflow still includes configuring models, creating a dataset, uploading and parsing files, and inspecting the resulting chunks. A simpler selector does not make one parser appropriate for every document. Teams should use representative tables, scans and content spanning pages to check what was actually extracted. An upload-success indicator is not evidence that the resulting retrieval material preserves the relationships needed to answer a later question.

What should survive a pause

One included recovery fix is specific: parallel items should restore saved outputs and variables after repeated pauses without rerunning completed steps. This concerns factual continuity of a workflow, and it was not independently reproduced here. The conversation guide also distinguishes temporary attachments from permanent knowledge-base entries. Stopping generation should not be interpreted as reversing earlier parsing or external calls. Acceptance should inspect completed results, pending work, attachment scope and citation sources separately. A resumed progress display is not sufficient if the underlying material changes or a branch disappears. The final summary needs to correspond to the state that actually survived the interruption.

Deployment boundaries remain unresolved

The release announces ARM64 Docker images, but the quickstart at the same tag still calls Linux ARM64 unsupported. This issue cannot resolve that source conflict or promise straightforward deployment there. The guide recommends starting with four CPU cores, 16 GB memory and 50 GB disk, plus chat and embedding models; that is neither a universal minimum nor a promise of free operation. Manual document search, fixed retrieval-based answering and other RAG frameworks remain alternatives. A pilot should compare total time to a supported answer, incorrect citations, migration effort and pause recovery. More agent steps do not improve the product if they add calls without reducing the checking people still perform. Record the exact parser, model and document revision for reproducibility.
