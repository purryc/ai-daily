Preferences need operational meaning

A request not to remember something can mean removing chat history, avoiding a profile, or excluding later recall. One switch struggles to express those distinctions. Submitted on October 21, this paper separates participation, collection, secondary use, persistence and autonomy, then audits 788 settings or actions across 30 products. The authors classify 567 within the taxonomy, including only 21 concerning persistence. That snapshot illustrates uneven controls; it does not establish the present configuration of every product. The contribution is a vocabulary and eight executable examples for platform engineers translating preferences into operational checks, rather than certification of an existing service.

Propagation needs an enforcement point

In a travel-planning prototype, an orchestrator passes restrictions through a search agent and tool. It can still assemble an itinerary while rejecting prohibited profile writes, logging or history reads. MCP and A2A carry custom metadata here; the work does not establish a universal privacy-enforcement standard built into either protocol. Other examples separate analytics, training and advertising, recheck consent versions for newly introduced tool categories, and distinguish retained conversation from future recall and behavioral profiling. Changes should be checked before the operation with an external effect, not only at chat entry. For implementers, the concrete deliverable is a mapping from each control to the execution paths it governs.

Show where control ends

The paper preserves two boundaries that a product pitch could obscure. A destination honoring an opt-out does not make the model provider’s orchestration logs invisible. Blocking a profile write also does not mean a classifier never computed the inference. These prototypes primarily govern prospective collection, use and action, not retrospective deletion. The public repository is MIT-licensed and explicitly experimental; it was not executed here, and recipient-side storage was not independently inspected. An alternate network path could bypass an otherwise complete preference chain. The interface should therefore explain which locations are controlled and which remain dependent on another service’s behavior.

Evaluate observable effects

Alternatives include temporary conversations, globally disabling memory, approving each tool call and maintaining purpose allowlists manually. They can be simpler while sacrificing useful continuity. A falsifiable pilot should first identify operations that must remain possible, then introduce prohibited writes, mid-task preference changes, new tools and retries with uncertain outcomes. Inspect destination records, logs and approval evidence rather than trusting the agent’s acknowledgment. The paper’s approval flow keeps permission outside the model and binds it to the final request, supplying a testable design rather than a verified recovery guarantee. If legitimate work becomes impossible, or rejected content persists through another path, the controls have not completed the user’s privacy task. Approval and retry behavior must also distinguish an operation that certainly failed from one whose external result is unknown; repeating the latter can create an additional effect.
