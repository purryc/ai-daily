A second machine handles the Apple build

An agent changing an iOS app may already have its code and backend on Linux; Xcode and the Apple build are the pieces that need a Mac. Amp’s October 29 release makes a Mac a second machine attached to the thread while the main agent and development server stay on the orb. The vendor describes startup in roughly thirty seconds, a claim rather than an independent timing measurement. Screenshots, logs and build outputs return to the same conversation, avoiding a separate explanation of the task. This split fits an established Linux toolchain, but project dependencies, signing arrangements and durable outputs still need a plan. A disposable satellite is not a persistent development workstation.

Code synchronization has a defined boundary

The documentation makes synchronization more precise: changed files are copied before each command on the Mac, while Git-ignored material such as a local environment file stays behind. Images include Xcode, iOS simulators and Homebrew; a project can select an image or pin an Xcode version that guides selection. Apps can reach a backend on the orb. The Mac tab streams the desktop and allows clicks and typing, so a person can inspect the result the agent describes. That makes the handoff observable through screen, logs and report. A successful simulator view still does not establish real-device performance or correct behavior for notifications and device-specific features.

Waiting and inspection affect compute cost

Satellites have two published rates, two and four dollars per hour, charged against included orb usage and then credits. A Mac stays available for twenty minutes after its last use so a follow-up can reuse build caches. The documentation counts a long build and an open Mac tab as use. Once idle time expires, the machine and its local state are deleted; archiving the thread, sleeping the orb or asking it to stop also ends it. Amp’s general pricing separates agent-model usage from compute, so token charges alone do not estimate a full job. The temporary cache can help repeated revisions, while leaving the inspection view open affects actual consumption.

Visual replies provide another inspectable result

Amp also announced interactive charts, timelines, diagrams and mockups inside threads that day. Its examples include a repository-history view and several compact ways to show a diff statistic inside a button. These let a developer compare presentations before choosing one to implement. They complement the satellite’s actual build workflow; an interactive sketch is not proof that the application has been built or tested. The examples come from vendor-authored threads. Satellite access still requires an experimental-settings waitlist and expands with capacity, without a guaranteed admission date. Before adoption, a team needs account eligibility, a reproducible temporary build environment, a destination for outputs and a clear point for human takeover.

Other access changes have their own dates

Two access changes earlier in the week have separate dates. On October 28, individuals gained the ability to add a self-hosted provider in their own Orbs settings. The thread composer identifies it as Personal under Self-Hosted, removing the previous requirement for workspace membership and administrator management. The October 27 Android app shows threads, Portal previews and code differences in Changes, providing another place to inspect agent work. These expand deployment and viewing access; they do not establish general availability of Mac satellites, whose beta waitlist remains a separate condition.
