GA applies to the tool interface

The October 30 Gemini API changelog marks Computer Use generally available across Interactions and GenerateContent. It takes a task and screen images and produces clicks, typing or other interface actions for workflows such as forms, interface testing and cross-site research. This event is distinct from previous Gemini model launches, Genie world simulation and consumer file editing. Nor should every capability in today’s documentation be counted as newly introduced that day. Integrators receive a way for the model to propose the next interface action; they still supply a real browser, mobile or desktop environment. For tasks with a suitable programmatic API, that remains an alternative. Screen control is useful where access or relevant state lives in an interface.

The application must keep the loop running

The documentation separates the loop into observable steps: provide a screenshot and goal, receive function calls, map actions to the real screen, execute them, and capture the resulting state. History must retain both the model’s action and the client’s response so the next turn reflects what happened. Current actions include an intent field describing their purpose, but that explanation is not evidence of successful execution. If a button fails, a popup appears or a page is still loading, the client needs to return the actual state rather than assume the previous screen remains valid. GA does not remove the loop, waiting logic or error handling. It changes how the next action can be chosen.

Confirmation belongs in the executor

The model can return require_confirmation, which the integrator must turn into a real human handoff rather than merely logging the explanation. Policy categories cover payments, communications, account creation, data modification and consent-related actions. Even configured preferences do not eliminate the need to handle a returned confirmation decision. Screenshot prompt-injection detection is opt-in and defaults to false. It checks for adversarial instructions in the visible environment; it does not make every external page trustworthy. In a usable agent, the confirmation surface should show the task, current screen and proposed action together. After approval, obtaining current state helps prevent execution of a step whose screen context has already changed.

The reference implementation shows the runtime work

The official reference repository offers local Playwright and Browserbase execution paths and requires model access plus browser dependencies. Its name still contains preview, which should not override the dated GA announcement. Its README also records a practical capture problem: native select menus on some operating systems may not appear correctly in screenshots, leaving the model without the relevant options. The bottleneck can therefore be capture rather than reasoning. Model, browser and client versions should be recorded together with the result. The pricing table lists Computer Use as unavailable on the free tier and billed at ordinary model input and output rates on the paid tier. There is no universal fixed per-task price; cost depends on the selected model, actual turns and execution environment. Initial integration is easier to assess with inspectable tasks and explicit stopping conditions.
