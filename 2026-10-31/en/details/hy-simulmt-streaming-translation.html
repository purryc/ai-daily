Translation arrives while the speaker continues

An English-speaking listener following a Chinese presentation need not wait for a complete recording before seeing a translation. Tencent Hunyuan released Hy-SimulMT on October 26 to accept incoming audio continuously and produce translated text as speech continues; English-to-Chinese translation is also supported. In the SimulInfer browser interface, the operator chooses a direction, permits microphone access, starts the conversation, then stops and finishes it. An audio file is another input option. This changes the waiting sequence of recording, transcribing and translating a complete passage. The ordinary checkpoint returns translation only, while an Interleave checkpoint supplies source text as well. The deployed model determines what the page displays, providing a useful original-language reference when somebody needs to check a technical term.

Preserving the voice requires another service

Translation and speech synthesis are separate parts of the system. The documented voice-cloning path deploys Qwen3-TTS as another service, adds its address and model to the configuration, and enables speech output after restarting SimulInfer. The reference voice can come from the uploaded recording or microphone input, without an additional reference transcript. Tencent’s demonstrations show translated speech and retained vocal characteristics, but the authors explicitly describe the videos as offline replays. Their playback cannot establish live first-audio latency. A meeting integration therefore needs to maintain both the translation service and the speech service, and check how text and audio stay aligned. Downloading the translation weights alone does not create an operational bilingual calling system.

How short audio blocks become browser text

SimulInfer normally processes audio in 1,600-millisecond blocks. Its short-chunk mode still requires that initial block, then permits 800-millisecond blocks afterwards. The cadence is a service configuration, not a switch that appears in the browser. Deployment needs a compatible inference backend, sufficient GPU memory and audio dependencies; the web service can run on a separate CPU machine. Remote browser microphone access requires HTTPS, and a proxy must support WebSocket traffic. File streaming and continuous audio input are available to application developers, who must also signal the end of input and read the final response. These requirements matter when embedding translation into a meeting page: a browser interface removes some user interaction work but leaves server deployment and transport configuration with the integrator.

The three-second result is not a complete call measurement

Tencent reports roughly three seconds of StreamLAAL on the RealSI long-audio evaluation. That metric measures streaming translation lag, not the time until a loudspeaker produces the first translated sound, and does not establish the experience on an arbitrary meeting network. Another vendor comparison used eighteen recordings of about six minutes and six professional interpreters. Its conclusion of comparable quality applies to that sample, not every accent, overlapping discussion or noisy venue. The model and project use Apache-2.0, with original terms retained for third-party components. Deployment still has integration limits: the documentation says llama.cpp support has not merged, so the existence of GGUF weights does not prove compatibility with every client. Teams can begin with their own low-risk meeting material, listening for terminology, corrections and the transition into synthesized speech.
