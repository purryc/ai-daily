A new report: work continues while the user loses feedback

Hermes Desktop is a native surface for people who want one agent to work across files, tools and conversations. The official README describes model and provider settings, live tool activity, a file browser and side-by-side previews, using the same configuration, sessions, skills and memory as the CLI and gateway. The concrete news here is a community report opened on October 19, not another launch of Hermes. Issue #141485 describes repeated freezes while tools were running on native Windows 11 even though the backend process remained alive. The reporter identifies Hermes 0.22.2, a particular code commit, a desktop package stamped September 17, and Python 3.14.7. That combination matters: it cannot stand for every installation of the current release. GitHub records creation at 10:01:40 UTC on October 19, before this edition’s preceding twenty-four-hour window, so this is a near-three-day supplement. The attached log excerpts identify October 19 in an unspecified local timezone. We count one new community observation and no new product-release event. Neither its cause nor its severity has been independently reproduced by this publication.

The workflow failure: status reads compete with tool execution

The intended chain is straightforward: open an existing installation, describe the task, let the agent invoke tools, watch progress in the desktop window, and inspect the returned result. In this report the work included computer-use enumeration through Windows UI Automation and a terminal search across a whole drive for that day’s documents. Backend excerpts show event-loop stalls around thirty-seven to forty-five seconds, while status and session-message requests time out. These are diagnostic observations from one machine, not population statistics or a measured failure rate.

[S13]

Losing progress feedback changes the next decision

The interaction failure is more specific than a slow answer. If the status and message requests needed to paint the conversation queue behind the same busy execution path, the user loses the information needed to decide whether to wait, cancel, or try again. A spinner does not establish that an action is still making useful progress. The reporter also supplies available-memory figures and an absence of detected memory exhaustion, which argues against reflexively treating the symptom as an oversized-model problem. Those logs still do not independently prove that Python’s GIL is the sole cause, or exclude an interaction with the desktop build and concurrent processes.

[S13]

Available controls and adoption costs: avoiding triggers is not a fix

The reporter’s local workaround disables computer use by default and uses a pre-tool-call hook to reject recursive searches rooted at an entire drive. That narrows the tasks available to the agent; it does not demonstrate a backend fix. The single reply links the report to an existing resource-consumption tracker. Its GitHub author association is NONE, so we do not describe it as maintainer confirmation or a promised repair. The official 0.22.2 release note provides a separate adoption concern: 0.22.1 had been built from the wrong commit, and 0.22.2 restores the intended release line. It also warns that some sessions used with the 0.22.1 gateway cannot be deleted in 0.22.2. It does not claim to repair this later report.

Installation channels and alternative workflows

The desktop README instructs users to update through the owner of the artifact: Store packages, App Installer packages, macOS bundles and source checkouts have different update paths; a source updater does not rewrite a bundled payload. The practical manual alternative is to locate the relevant folder or files first and give the agent a bounded input. That trades a small amount of human preparation for a narrower execution scope. The CLI is another supported surface for the same core, but shared backend state makes it inappropriate to present switching interfaces as a verified cure.

Product judgment: the control path must remain reachable under load

For a product manager, the evidence supports a testable design hypothesis: a long-running task needs a control and observation path that remains usable when an expensive tool is under pressure. A useful interface would preserve the last trustworthy status, the identity of the active tool, elapsed time, and the actions already acknowledged. This is editorial analysis, not a claim that Hermes currently provides independent cancellation, complete rollback or automatic recovery in this failure state. A bounded validation would compare the same task with a restricted directory search and a whole-drive search, then with computer use enabled and disabled, on an isolated test machine. Record status-response latency, the response to a cancellation request, and whether recovery produces duplicated artifacts. Keep the software build fixed and retain unsuccessful traces. If a current stable installation does not reproduce the problem, or the blocking mechanism differs, the hypothesis must be revised. Users need recoverable control; team adopters also need a supportable installation channel and version consistency. Model and hosting costs were not priced in this check. It is not a screenshot of this Windows failure and provides no evidence of task-completion reliability.
