Who it serves: short-workflow experimenters

The plausible user is an experimenter who is willing to maintain a small development board in order to let a visual agent operate existing iPhone apps. A bounded task is changing an alarm to 7:30 on weekdays and giving it a label. That is a more useful starting point than an open-ended request to manage the phone. The author's repository links an alarm demonstration, but this review verified documentation and a pinned commit, not a physical installation or a measured success rate. The latest verified commit before the original cutoff is October 20 at 10:21:22Z; its message describes preserving restored Bluetooth subscriptions and reducing RTC memory use. That establishes repository state, not the project's original launch. Discovery came through an October 14 report about Henry's earlier approach and an October 19 comment by this project's builder. Workflow: the phone observes; the board supplies input

The October 14 report describes the earlier route as AirPlay capture through UxPlay and GStreamer to a computer running the model, with an ESP32-S3 delivering USB HID input. This project's route puts the interface, conversation, screen capture and agent loop in Safari on the phone. The user starts screen sharing and gives a goal. Harness sends selected context to the chosen model, validates an action plan, and transfers taps, drags, key presses and waits over local WebRTC to the ESP32. The board then supplies Bluetooth HID input. A fresh screen observation closes the loop. The phone no longer needs the same USB tether or a computer running the agent loop, but the bridge still needs power. Initial firmware installation still uses desktop Chrome or Edge. State and adoption: a receipt is not completion

The pinned architecture distinguishes receipts for submitted commands from evidence that the screen actually changed. The runtime checks fresh observations and reconciles interrupted input before continuing. Stopping screen sharing pauses the task, and the user decides when to resume. By default, completion returns to the Harness conversation and checks that it is visible. With two connections, each page must select the correct phone, and each phone has one active writer. These are more consequential failure boundaries than conversational fluency. Adoption requires iOS or iPadOS 27+, accessibility and Bluetooth pairing, a shared Wi-Fi network, model access and continuous bridge power. The author estimates a basic ESP32-C3 board at roughly two US dollars. That is an author estimate for the board alone, not a verified retail quotation or total cost: power, cables, model usage, setup time and maintenance remain. The repository uses MIT terms, requiring the notice to accompany substantial copies and providing no warranty. Browser-local sessions do not make this offline: selected context still goes to the model.

Market hypothesis: broader coverage must earn its recovery cost

PM inference: treating phone control as a replaceable peripheral creates a possible automation entry point for apps without a usable business API. For a single alarm task, however, the first alternatives are manual setup and existing system automation. Broader visual-agent coverage becomes valuable only when a workflow crosses apps those routes cannot reach, and that benefit must pay for device maintenance. Wireless operation improves the physical setup; it does not establish reliability. A falsifiable evaluation would run ten identical alarm edits, interrupt sharing just after input, switch away from the page, and change the Bluetooth target. Measure correct final states, duplicate actions, repeated user explanations and elapsed time after recovery. If the result is harder to verify, task scope should not expand yet. The accompanying image is the author's actual interface with sample conversation. It visibly reports that the bridge is disconnected and screen sharing is off, so its completion text is not evidence of a successful physical run.
