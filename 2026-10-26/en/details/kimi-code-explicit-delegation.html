Kimi Code CLI 2.3.2 · Product update · maintainer release and implementation

Kimi Code requires a user choice before starting an agent swarm

2026-10-25T07:59:14Z · Released October 25 at 07:59 UTC, before the previous cutoff; included as a late-discovered supplement.

A large task no longer implies delegation

A developer asking Kimi to inspect a collection of files could previously find that the assistant had started a group of agents before returning a combined answer. Version 2.3.2 changes who makes that decision. The main agent is now instructed to handle ordinary work with its own tools; a message, project instruction file, skill or user-enabled multi-agent mode must explicitly request delegation. Asking for depth, research or a multipart task does not itself qualify. A developer can still request an explore agent by name, and an already authorized subtask can continue without another request. This is a client behavior change, separate from the K3.1 Pro model and long-context API capabilities covered previously.

The swarm switch is checked during execution

Batch delegation has a stronger boundary. The user can enable it with /swarm on, or use /swarm followed by a task to enable the mode and submit work together. The task form switches the mode off after a normal completion. The implementation checks the mode when resolving the call and again immediately before execution, covering the case where the user switches it off in between. With the mode off, the call returns an error without starting agents or offering a new approval dialog. Restoring an old session also ignores records where the tool had automatically activated swarm mode. The historical marker remains, but it no longer reactivates the mode for another turn.

Separate contexts still need a careful handoff

An ordinary subagent receives a task description, works in an independent context, and returns a conclusion to the main agent. The main agent remains responsible for the answer the user sees. Keeping intermediate files and tool records out of the main conversation can reduce clutter, but the delegated worker cannot see everything the parent already understands. The handoff therefore needs the goal, known facts and a bounded scope. Maintainers identify repeated context acquisition and its token cost as reasons for the change. For ordinary Agent calls, this release changes system and tool instructions; that is distinct from the runtime rejection implemented for AgentSwarm. Deliberate parallel work still needs clear assignments and a final check that the combined answer addresses the original request.

Scripts and editors lose a previous route

The tighter rule removes a previous capability from some entry points. Print mode, invoked with kimi -p, and ACP clients such as Zed have no switch for enabling swarm mode, so they can no longer depend on the model to start AgentSwarm. A custom subagent also cannot borrow the main agent's switch to start a nested swarm. Interactive terminal, web and desktop users retain an explicit control. The CLI release should not be read as proof that every editor extension updated simultaneously. For someone who embedded batch inspection in a script, this needs a migration decision. The evidence establishes the published implementation and maintainer validation, not an independently measured reduction in total time or cost.
