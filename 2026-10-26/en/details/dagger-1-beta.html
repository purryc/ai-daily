Native project settings enter one workspace

Dagger 1.0 beta introduces a workspace, usually one Git repository, with modules and settings declared in dagger.toml. Modules read native toolchain configuration and load source files when required. The Go module, for example, follows local dependencies in go.mod and prepares a container with the specified Go version. A separate dagger.lock pins modules, images and Git or HTTP sources. This reduces duplicated environment settings and unnecessary file ingestion, particularly in monorepos, while leaving teams responsible for choosing modules and checking discovered project coverage. The feature changelog is dated October 22 and the broader announcement October 23; this record therefore belongs to the week supplement rather than the main daily window.

Find the failed test and inspect its container

Official modules attach OpenTelemetry test spans, giving the terminal and cloud interface separate status, duration and logs for each test, plus a rerun link. Selection granularity differs: Go can choose an individual test, while Vitest, Jest, Playwright and pytest select files. When a check fails, dagger check -i opens a shell in the container state where the command failed, reducing the need to reconstruct its environment manually. A related feature lets tests call Dagger modules through generated typed clients, for example to start their own database dependency. That self-orchestrating path supports Go first. It should not be read as identical integration-test support across all languages or frameworks.

Preview configuration and command changes

Existing projects can initially keep dagger.json, but the new structure separates workspace settings into dagger.toml and module metadata into dagger-module.toml. The migration command offers a preview showing file changes without applying them. When a coding agent invokes migration, Dagger requires an explicit preview or apply choice. Migrated modules also need generated SDK code committed; missing generated files are no longer supplied automatically at runtime. Compatibility is not merely a collection of aliases: dagger shell changes meaning, dagger develop disappears, and a root-level module may need explicit loading. Teams should review script entry points together with the configuration diff, regenerate code, and confirm the commands used locally and by CI still do the intended work.

Cloud checks and billing follow actual runs

Cloud Checks connects a repository to Dagger Cloud, runs dagger check after pushes and pull requests, and returns results to GitHub statuses and the cloud interface. Installation documentation lists macOS, Linux and Windows; the core repository uses Apache 2.0, while hosted execution is separately priced. Billing measures CPU, memory, inputs and outputs. Operations with the same inputs as work performed during the previous thirty days receive the lower repeat-work rate even if execution does not actually hit cache. The Starter plan is twenty dollars monthly, and the bill is the higher of the plan minimum or measured usage. Vendor speed examples were not independently reproduced here; beta migration and actual savings remain project-specific.
