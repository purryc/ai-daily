LangGraph exposes the checkpoint where a run actually stopped

The pause follows a saved state

A workflow might prepare an order and then pause after a node for human review. LangGraph had already saved that state, but normally emitted its checkpoint when the next execution tick prepared subsequent tasks. An interrupt-after pause or exhausted recursion limit could stop the run before that notification occurred. The maintainer reports that a client resuming from the last checkpoint it received could execute the final node again. Version 1.2.18 emits the stopping checkpoint on both exit paths. It repairs the gap between persisted state and the state visible to a client; it does not introduce a complete business approval product.

Recovery across execution paths

A separate fix concerns a node’s error_handler. Even after that handler dealt with an exception, executor paths used by message or custom streaming, subgraphs or parallel nodes could raise the original error again on exit. Executors now recognize handled task failures. Clients subscribing only to task or debug streams could also miss a failed task’s result because the single-task fast path raised before its event queue was drained. The change allows the error result to reach the stream first. A surrounding interface can consequently describe the failing node instead of receiving only an unexplained run-level exception, although the application must still decide what recovery to offer.

Snapshot frequency changes the tradeoff

DeltaChannel also changes its default full-snapshot interval from one thousand updates to one hundred. A shorter chain means less state reconstruction when reading long threads, at the cost of storing more complete snapshots. Teams can retain the previous interval through snapshot_frequency. This is not evidence of a universal tenfold speed improvement: the release supplies no benchmark covering every workload. Frequently updated large states and small states have different storage costs. Checkpoint size, reading frequency and retention time still determine the operating tradeoff. The change provides a default that favors reads and a setting to adjust it, rather than an unconditional performance promise.

Knowing what a resume will repeat

For a product team, the practical benefit is a closer match between completed, waiting and failed states in the interface and the underlying persisted execution. A staging workflow can pause immediately after a node, then verify that its new checkpoint identifies the same resume position. A parallel-node failure handled successfully should not still appear as an unexplained crash of the entire task. Checkpoints do not reverse an email or payment already sent; external actions continue to need idempotency, confirmation or compensation. Clients that assumed no final event arrived on stopping must also update their event handling. During an approval pause, the product can show which node has finished and what will happen next. That makes a resume distinguishable from restarting the whole task.
