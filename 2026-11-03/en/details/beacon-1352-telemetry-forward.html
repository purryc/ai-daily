Memory capture should preserve existing reporting

Beacon gathers history across coding agents and makes reviewed lessons available to subsequent work. That can help a developer carry project conventions between tools, but a team may already send Claude Code or Codex telemetry to another service. The merged change identifies a concrete installation conflict: redirecting those runtimes to Beacon’s local collector interrupted the previous backend’s feed. Version 1.3.52 adds forwarding to a second destination. This is an integration change, not proof that every agent becomes more capable through memory. Nor should the recent Product Hunt appearance be treated as the first release of an existing cross-tool memory product.

Capture and forwarding have separate boundaries

The forwarding pipeline can filter by runtime, with Claude Code and Codex as defaults, then redact and batch the selected data. Its queue and retries are bounded to prevent an unavailable destination from stalling Beacon’s own records. During adoption, compare the same event at both ends rather than checking only connection status. Inspect timestamps, identities, usage fields, removed content and any interval lost during an outage. A report can look healthy while undercounting costs if usage values are mistakenly redacted as secrets. Correcting that error must not expose actual credentials. These are practical acceptance questions; no independent delivery or redaction test was performed here.

Inspect the installation choice

The repository distinguishes local records, viewing tools and managed forwarding. Interactive setup preselects Beacon Cloud and starts forwarding after confirmation, while providing a local choice; signing in alone does not send data. A terminal browser and read-only local dashboard can inspect retained history. Teams handling client code or internal discussions should inspect the actual destination and capture scope rather than relying on the phrase local-first. Session history can include prompts, file activity and approvals, which is a broader information set than a token-usage table. Whether that history may leave a workstation is a separate decision from whether retaining it locally is useful.

Retained lessons need correction

The public repository uses an MIT license and provides installation paths for several platforms. Hosted-service charges and the cost of a particular workflow were not verified. Maintaining project notes, saving debugging records and retaining the existing observability service remain meaningful alternatives. A useful trial takes one solved problem, lets a later session reuse the lesson, then changes the project conditions and checks whether the stale rule can be identified and revised. Less repeated prompting is helpful only if old instructions do not create repeated mistakes. This release improves telemetry continuity; memory correctness, time savings and data-handling assurances still require separate evaluation.
