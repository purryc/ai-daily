WeKnora adds a workspace assistant with delegation and approval waits

Assigning work beside the knowledge base

WeKnora already uses team documents for retrieval, reasoning tasks and a maintained wiki. Version 0.9.0 adds an assistant beside the logo, opening a right-hand panel with context from the current knowledge base, document or settings page. A user can ask it to configure an event-planning agent, diagnose a failed document parse or turn a recurring research job into an automation. Bundled product documentation and management operations let it explain settings and act as the current user. Page context helps interpret references such as “this document”; it does not confine retrieval to the visible knowledge base. Users still choose documents, bases or tags with @ when scope matters. Private assistant history preserves unfinished work, while the user supplies the objective and relevant material.

Separate subtasks with visible progress

Independent parts of research or document organization can go to temporary collaborators or an existing reasoning-agent template in the same workspace. Each subtask has a separate conversation, visible progress, outputs and pending decisions; the main task collects the results. This changes the handoff burden: a child does not automatically receive the parent’s entire history or attachments, so its instructions need sufficient background and an explicit source scope. The documentation allows up to sixteen collaborators per task, with three running concurrently; approval waits do not consume running slots, and children cannot recursively create another layer. Users can add requirements or stop work. Stopping the main task cancels running collaborators, but completed writes remain. Collaboration also preserves the original limits on accessible resources.

Schedules keep results and waiting states

Recurring summaries can be created conversationally or in an automation form specifying the task, one-time or Cron schedule, timezone, model and notifications. Users can keep a conversation for accumulating context or start a fresh one for each run, optionally carrying the previous successful result. The next execution time is previewed before use. Jobs run with their creator’s current identity, so later permission changes still matter. An approval pauses execution and produces a notification; cancelling one run leaves the schedule intact. Three consecutive failures pause the plan automatically. After an interruption, an uncertain result requires attention instead of blindly repeating a possible write. This can maintain recurring knowledge checks, provided the deployed application stays running; a sleeping computer cannot deliver its scheduled work.

[S77]

Different kinds of writes retain different controls

Sessions offer read-only access, confirmation before changes or automatic ordinary writes. A one-off approval cannot override read-only mode. Automatic execution still asks before destructive operations and tools configured for mandatory approval. Persisted prompts and resumable state let a user refresh the page without recreating the request. Session grants and longer-lived automation grants have separate scopes; neither overrides role permissions. Deployment also requires the release’s database migrations and attention to Feishu resynchronization. Reusing a sandbox per user is an optional configuration, and separate working directories on one machine are not operating-system isolation. The October 29 release establishes these additions to the product, while retrieval quality and successful task completion still depend on the chosen models, available tools and source material.
