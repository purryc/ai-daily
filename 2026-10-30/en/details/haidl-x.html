Bring the notebook state into the request

In a computational notebook, asking why something failed depends on the current code, its output and preceding attempts. A separate chat transcript makes it difficult to reconstruct the state that motivated an answer or whether the user acted on it. HAIDL-X operates as JupyterLab middleware so users request help without leaving the notebook. Its frontend packages code, execution output, errors and timing for a backend that builds context, calls the chosen model and returns the response to the notebook. User feedback can be associated with the same request. The change connects assistance to the work in progress; it does not automatically certify code correctness from logs or replace an instructor's assessment.

Store a complete interaction object

The paper's HAIDL representation places metadata, request, prompt payload, AI response, feedback, problem context and model information in one object. The runtime persists completed objects in MongoDB, while a separate provider layer handles differing model interfaces. Switching a model need not change the analysis format. Queries can retrieve all requests for an assignment, requests containing error output or a time-ordered interaction trajectory. That structure helps reconstruct what someone asked under which conditions, reducing retrospective stitching of disconnected logs. It still requires explicit choices about capture and interpretation rules. More complete records do not automatically reveal a person's intention, and retrieving a recorded exchange is different from guaranteeing an identical answer on another model run.

The same absence can describe different behavior

The classroom deployment involved 35 students, four programming assignments and about 800 interactions, organized into 140 student-assignment pairs. Analysis combines interaction objects with submitted notebook execution traces and the assigned access condition. Zero requests can accompany successful execution or repeated difficulty without seeking help; the chat log alone cannot distinguish them. Access followed a crossover arrangement, but some authorized students never used the assistant and some use occurred outside assigned conditions. The authors preserve that difference between schedule and observation. Successful execution means no Jupyter execution error, not a correct algorithm or answer. Engagement, performance and learner categories are research labels derived from explicit rules and must be interpreted through those observable inputs.

Recording overhead is separate from learning benefit

The authors measure capture, object construction and persistence overhead beyond the model call. It stays within 25 milliseconds in the tested concurrency and provider configurations. Median record size is 4.53 kilobytes, varying with code, tracebacks and response length. These measurements establish modest costs for this implementation, not a universal deployment guarantee. The study aims to distinguish otherwise ambiguous collaboration patterns; it does not estimate a causal effect on learning outcomes. Integration also sends configured code and error context to an AI provider and persists records in a database, so capture scope depends on the actual work. Connecting requests with preceding and subsequent executions distinguishes apparently similar usage counts. These traces still cannot establish whether a student understood an answer or reconstruct learning outside the captured assignments.
