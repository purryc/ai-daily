Start a workflow from a request

Refunds and order handling often already have a fixed sequence, but connecting a conversational agent can require another tool wrapper. The new Step Functions connector exposes existing Standard and Express state machines through AgentCore Gateway. The agent chooses when to start and supplies input; the workflow retains its defined steps. In the announcement’s refund example, eligibility, manager approval and credit remain part of that sequence. For a product team, the first decision is which tasks already have a stable process worth reusing. A conversational entrance does not eliminate exceptional cases or the people who handle them. It changes how work is requested, while keeping the operational procedure available for inspection.

Make the tool boundary explicit

An administrator selects the exposed operations and pins the state-machine identifier on the Gateway target. That fixed parameter is omitted from the tool schema, preventing an agent from choosing another workflow by supplying a different identifier. Gateway handles schema generation and the service call. Starting work returns an execution identifier for later inspection. This removes connection code and interface maintenance rather than the need to model a business process. A workflow can faithfully execute an incorrectly interpreted amount or customer reference. The application therefore needs field, identity and business-precondition checks at its input boundary; syntactically valid JSON is only one small part of acceptance.

[S101]

Separate pinned workflows from execution access

The connector exposes ten operations, with four accepting a pinned state machine. Other operations inspect or stop an execution using an execution identifier; the Gateway service role determines their reach. Task-token operations have a separate boundary, so pinning a workflow is not a universal restriction on every tool. For a shared platform, that distinction affects how gateways are separated and who can read sensitive inputs or outputs. The operator-facing application should also distinguish an accepted start, continuing execution, failure and business completion. Receiving an execution identifier is useful acknowledgment, but is not evidence that a refund or another downstream result already exists.

[S102]

Choose the right feedback contract

The tutorial uses Standard because its execution listing, description and history operations are unavailable for Express executions. Synchronous Express can instead return a result in the same call. A long-running task therefore needs a deliberate feedback contract rather than a single generic completion indicator. Availability follows AgentCore Gateway regions, with normal Step Functions and Gateway charges. Teams that already own state machines may remove an adaptation layer; teams without mature processes still need to define steps, permissions, failure behavior and maintenance. No paid resources were created for this report, and no performance or time-saving result was measured. A practical comparison is the wrapper code removed versus the exception explanation and human handoff that remain.
