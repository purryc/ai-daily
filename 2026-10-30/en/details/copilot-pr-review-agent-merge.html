Choosing extra review for a difficult change

A change to authentication or a shared library can have consequences beyond the file being edited. Max, now in public preview, runs multiple review agents using models from different providers, then asks an aggregation agent to reconcile findings and check disagreements before returning one review. It can be chosen for a particular pull request, with defaults and maximum allowed effort configured at repository, organization or enterprise level. GitHub says the additional work takes longer and consumes more AI credits than Lite or Balanced. Multiple models describe the mechanism, not a measured defect-detection guarantee for the reader’s repository. A maintainer still needs to connect each proposed issue to a code path and relevant test conditions.

A review and a required approval are separate settings

The October 28 release makes Copilot approvals generally available, while leaving them off by default. Configuration documentation separates allowing an approving review from allowing that approval to satisfy merge requirements. Enabling the former alone should not be described as giving Copilot the final release gate. File patterns can narrow which pull requests count: every changed file must match an allowed glob, while an empty list covers all files. New commits dismiss a previous Copilot approval and require a fresh review. That ties a decision to the inspected version. It also matters after automated repair, because the earlier judgment concerned different code. Teams should inspect effort, counting and path settings together rather than rely on a reassuring overview comment.

Starting repair when the selected blocker appears

Agent Merge previously existed in the Copilot app and VS Code; the new entry point is the merge box on GitHub pull requests. Watch and fix lets the user select failed Actions workflows, merge conflicts or both. A selected blocker triggers work in a cloud development environment, with status in the merge box and a timeline event explaining why the agent started. A personal setting can make this behavior the default for future pull requests. It reduces repeated CI checking and the handoff needed to start another repair task. The resulting change still deserves inspection: making a test pass and preserving the intended behavior are separate goals, and a repair can succeed at one while compromising the other.

Cloud repair retains repository and billing boundaries

The documentation requires paid cloud-agent access, applicable organization policies and the repository’s Enable automations policy. Fork pull requests and stacked pull requests are unsupported. Repairs run in an Actions-based development environment using repository setup steps, instructions and skills, rather than the cloud sandbox used by some other agent tasks. AI credits are charged to whoever enables Agent Merge on that pull request, who may not be its author. Enabling repair does not enable auto-merge. When auto-merge is configured separately, GitHub merges only after required reviews and status checks are satisfied. A useful handoff therefore distinguishes watching, changed code, approval and actual merge; these are different states with different remaining responsibilities.
